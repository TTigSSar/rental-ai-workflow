### 3.1 Решения по цене — разбор вариантов

Выбор — в §3.2. Общее для всех вариантов:
- согласованные суммы (S2–S8 и итоговые) не пересчитываются никогда (§11.5 спецификации, как ADR-043 §4);
- по объявлениям с ценой «за день» ничего не меняется: формула B-2 для дня — та же N × цена.

**Факты из кода.**
- `TotalPrice` записывается один раз при создании (`BookingsService.cs:136`) и при одобрении не пересчитывается (`UpdateOwnerDecisionAsync`).
- Ожидающий запрос живёт не дольше 24 ч (`ExpiresAt`, `BookingsService.cs:138`). Значит, M-J касается только запросов, созданных за последние 24 ч перед переходом.
- По B-2 сумма для недели, месяца и года никогда не больше старой: ceil(N / k) ≤ N. Пересчёт S1 может только уменьшить сумму.
- «Час» сейчас доступен в форме и принимается сервером (`create-listing.model.ts:9-17`, `CreateListingRequest.cs:24`, `UpdateListingRequest.cs:21`). У почасовой цены нет правила B-2: аренда считается днями.

#### M-J — ожидающие запросы (S1) по ценам за неделю, месяц или год, созданные по старой формуле

| Вариант | Что происходит | Последствия | Риски |
|---|---|---|---|
| (1) Пересчитать при переходе | `TotalPrice` S1 пересчитывается по B-2, в чат пишется «Сумма пересчитана по новым правилам: было X, стало Y», арендатор уведомляется | Владелец принимает уже правильную сумму. Сумма только уменьшается | Владелец видел в запросе большую сумму. Нужен однократный идемпотентный шаг миграции и уведомление |
| (2) Не пересчитывать | Владелец может принять запрос со старой суммой | Ничего не меняется для пользователей | Арендатор может получить согласованную завышенную сумму (например, 49 000 ֏ вместо 7 000 ֏ за неделю). После принятия она уже не пересчитывается |
| (3) Отозвать с объяснением | Такие S1 переходят в T2 «запрос больше не действует, отправьте новый», обоим уведомление | Чистый старт по новой формуле | Автоматический итоговый переход, хотя и с объяснением (O-11 требует решения). Арендатор теряет запрос |
| (4) Запретить принятие и дождаться истечения | Одобрение S1 по старой формуле отклоняется («цена изменилась»), запрос истекает за ≤ 24 ч | Не нужен пересчёт | Владелец видит ошибку при принятии. Арендатор ждёт до 24 ч и всё равно получает «нет ответа» |

**Рекомендация:** (1). Сумма меняется только в пользу арендатора, ещё не согласована, а затронуты запросы не старше 24 ч. **Выбрано: (1), §3.2.**

#### M-K — объявления и брони с ценой «за час»

| Вариант | Что происходит с объявлением | Последствия | Риски |
|---|---|---|---|
| (1) Опубликовано, но не бронируется | Новые запросы недоступны, на странице «Владелец обновляет цену», владелец получает просьбу выбрать день, неделю, месяц или год. При редактировании «час» выбрать нельзя | Ничего не считается неверно. Владелец сам решает новую цену | Если владелец неактивен, объявление долго висит небронируемым. Может понадобиться правило скрытия из поиска через N дней |
| (2) Скрыть из поиска до правки | Как (1), но объявление не показывается в поиске и на карте | Арендаторы не видят небронируемое | Владелец может не понять, куда пропало объявление, нужно уведомление |
| (3) Автоматически сменить «час» на «день» с тем же числом | Цена 500 ֏/час становится 500 ֏/день | Объявление сразу бронируется | Меняет смысл цены без согласия владельца. Владелец может потерять деньги. **Не рекомендую** |
| (4) Вернуть на модерацию | Статус объявления меняется, нужна повторная проверка | Админ контролирует | Нагрузка на модерацию, владелец не понимает причину |

Брони по почасовым объявлениям:
- **S2–S8 и итоговые:** суммы не пересчитываются ни в одном варианте.
- **S1:** правила B-2 для часа нет, поэтому пересчитать нечем. Варианты:
  - (а) владелец может принять или отклонить запрос с той суммой, которую арендатор видел при отправке;
  - (б) отозвать с объяснением, как в M-J (3).

**Рекомендация:** (1) для объявлений и (а) для S1. Это не меняет ни согласованных сумм, ни смысла цены без согласия владельца. **Выбрано: (1) и (а), §3.2.**

Запросы для подсчёта — §4 (по `PriceUnit` и статусу).

## 4. Запросы для оценки объёма

Только чтение. Выполняет platform-engineer. Имена колонок проверить по текущей схеме до запуска.

Статусы: Pending 0, Approved 1, Rejected 2, Cancelled 3, Expired 4, Completed 5, ReturnMarked 6 (старое значение), Active 7. Даты сравниваются с ереванской датой, `@today`.

```sql
DECLARE @now datetime2 = SYSUTCDATETIME();
DECLARE @today date = CAST(DATEADD(hour, 4, @now) AS date);   -- Asia/Yerevan, UTC+4

SELECT 'MG-01 Pending live'          k, COUNT(*) n FROM Bookings WHERE Status = 0 AND ExpiresAt >  @now
UNION ALL SELECT 'MG-02 Pending stale',   COUNT(*) FROM Bookings WHERE Status = 0 AND ExpiresAt <= @now
UNION ALL SELECT 'MG-03 Approved future', COUNT(*) FROM Bookings WHERE Status = 1 AND EndDate >= @today
UNION ALL SELECT 'M-E Approved past',     COUNT(*) FROM Bookings WHERE Status = 1 AND EndDate <  @today
UNION ALL SELECT 'M-C Active',            COUNT(*) FROM Bookings WHERE Status = 7
UNION ALL SELECT 'M-D Active overdue',    COUNT(*) FROM Bookings WHERE Status = 7 AND DATEADD(day, 7, EndDate) < @today
UNION ALL SELECT 'MG-04 Completed w/ ActiveAt', COUNT(*) FROM Bookings WHERE Status = 5 AND ActiveAt IS NOT NULL
UNION ALL SELECT 'M-A Completed no ActiveAt',   COUNT(*) FROM Bookings WHERE Status = 5 AND ActiveAt IS NULL
UNION ALL SELECT 'M-B ReturnMarked (6)',  COUNT(*) FROM Bookings WHERE Status = 6
UNION ALL SELECT 'Unknown status',        COUNT(*) FROM Bookings WHERE Status NOT IN (0,1,2,3,4,5,6,7)
UNION ALL SELECT 'M-G no conversation',   COUNT(*) FROM Bookings b
          WHERE NOT EXISTS (SELECT 1 FROM Conversations c WHERE c.BookingId = b.Id)
UNION ALL SELECT 'M-F blocked party (non-terminal)', COUNT(*) FROM Bookings b
          JOIN Listings l ON l.Id = b.ListingId
          JOIN Users r ON r.Id = b.RenterId
          JOIN Users o ON o.Id = l.OwnerId
          WHERE b.Status IN (0,1,6,7) AND (r.IsBlocked = 1 OR o.IsBlocked = 1);

-- Цена (B-2). PriceUnit: Hourly 0, Daily 1, Weekly 2, Monthly 3, Yearly 4
SELECT PriceUnit, Status, COUNT(*) n FROM Listings GROUP BY PriceUnit, Status ORDER BY PriceUnit, Status;

SELECT l.PriceUnit, b.Status, COUNT(*) n, SUM(b.TotalPrice) total
FROM Bookings b JOIN Listings l ON l.Id = b.ListingId
WHERE l.PriceUnit <> 1
GROUP BY l.PriceUnit, b.Status ORDER BY l.PriceUnit, b.Status;   -- M-J (Status 0), M-K (PriceUnit 0)
```

Брони на объявлениях с ценой не за день: если их число больше нуля, их суммы были посчитаны старой формулой (дни × цена периода). Согласованные суммы (Status 1, 5, 7 и итоговые) **не пересчитываются** (§11.5 спецификации, как ADR-043 §4). Но владельцам и поддержке стоит знать, что по ним арендатор мог согласиться на завышенную сумму. Q-15 (А, по делегированию): поддержка получает список, пользователям автоматически ничего не сообщается.

## 5. Правила самой миграции (для этапа планирования)

1. Миграция идемпотентна. Повторный запуск не меняет уже перенесённые строки.
2. Для каждой перенесённой строки в журнал миграции записываются исходный статус, новое состояние, правило (MG-x или M-x) и время.
3. Итоговые состояния получают только строки MG-02, MG-04…MG-07, M-A (T1) и M-E (T2) — по выбранным вариантам §3.2.
4. Уведомления при миграции отправляются только там, где это прямо выбрано: M-J (арендатору) и M-K (владельцу). M-B, M-D, M-E и M-F уведомлений не дают. Отправка идёт в рабочее время по Еревану (тихие часы, Q-6), с ключами без дублей.
5. `TotalPrice` согласованных броней (S2–S8 и итоговых) миграция не меняет никогда. Снимок цены и единицы (Q-8) введён для новых броней. Для старых броней он не заполняется, изменение дат для них недоступно (Q-19, по делегированию). Пересчёт по B-2 — только для S1 по M-J (1).
6. Перед продакшеном миграция прогоняется на копии БД, отчёт сверяется с §4. Сам миграционный код проверяет человек (CLAUDE.md, правило для миграций).
7. Чаты перенесённых T1 и T2 из MG-02 и M-E становятся только для чтения (R-3, Q-18). Чаты старых Rejected, Cancelled и Expired остаются открытыми (M-H, только перенесённые данные).
