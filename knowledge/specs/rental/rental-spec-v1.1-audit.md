## A-1. Статусы и переходы (текущие)

**Есть.**
- `BookingStatus` (`RentalPlatform.Domain/Enums/BookingStatus.cs`): Pending 0, Approved 1, Rejected 2, Cancelled 3, Expired 4, Completed 5, Active 7. Значение 6 (ReturnMarked) выведено из оборота.
- Переходы (`RentalPlatform.Domain/BookingStatusTransitions.cs:13-23`): Pending → Approved | Rejected | Expired | Cancelled; Approved → Cancelled | Active; Active → Completed.
- Действия (`BookingsService.cs`):
  - создать (арендатор);
  - approve / reject (владелец, до `ExpiresAt`, строка 407);
  - cancel (только арендатор);
  - activate и complete (только владелец, без проверки дат).
- В интерфейсе остались мёртвые значения `PendingApproval`, `ReturnMarked`, `Archived` и `CompletionMethod` (`features/bookings/models/booking.model.ts:1-15`). Неизвестный статус, в том числе число 6, превращается в `'PendingApproval'` (`bookings-api.service.ts:28-33`), а `ownerMayDecide` показывает для него «Одобрить» (`booking-details-page.component.ts:142-147`).

**Расхождение.** Модель из 7 состояний не выражает S3, S4, S6, S7, S8, S9 и T3 из v1.1.

**Предложение (техн.).** Новые значения состояния (6 повторно не использовать) или поля-отметки плюс вычисляемое состояние. Выбор на этапе планирования, нужен ADR, миграцию проверяет человек.

## A-5. Время, часовой пояс, таймеры

**Есть.**
- В API всё в UTC:
  - проверка «начало не в прошлом» (`BookingsService.cs:482-486`);
  - отмена `StartDate <= today(UTC)` (`:239-240`);
  - `ExpiresAt = now + 24h` (`:138`);
  - плашка `return_due` (`Application/Common/ChatTokens.cs:69-74`).
- Нигде в rental-api нет `TimeZoneInfo`, Asia/Yerevan и логики тихих часов. В конфигурации нет переменной TZ.
- Планировщик один: `BookingExpiryBackgroundService` (раз в минуту, `:14`, `:45`). Он ничего не отправляет.
- В интерфейсе время смешанное:
  - `minDate` календаря и быстрый выбор — по местному времени (`booking-calendar.component.ts:105-109`, `listing-booking-page.component.ts:373-392`);
  - `canCancel` — по UTC (`booking-details-page.component.ts:240,252`, `shared/.../date.utils.ts:13`);
  - срочность на `my-booking-card` смешивает полночь UTC с текущим временем (`my-booking-card.component.ts:57-67`).

**Расхождение (C-07).** Между 00:00 и 04:00 по Еревану сервер считает «сегодня» вчерашним днём. Отмена в день начала проходит, «Срок возврата прошёл» появляется на 4 ч позже, а карточка показывает «вернуть завтра» в день возврата.

**Предложение.**
- Продукт: все календарные правила по Еревану, AC-25.
- Техн.: один серверный помощник «сегодня по Еревану», используемый везде. Таймеры TM-01…TM-08 и напоминания RM — в фоновой задаче с идемпотентными ключами. Армения не переходит на летнее время, но смещение должно браться из часового пояса, а не быть зашитым числом.

## A-6. Отмена

**Есть.**
- Отменяет только арендатор (`CancelAsync`, «Only the renter can cancel»).
- Pending — всегда. Approved — только пока `StartDate > today(UTC)`.
- Причина не запрашивается.
- Уведомления нет, строки в чате нет (`BookingsService.cs:206-253`).

**Расхождение (C-05, C-06).**
- O-1: владелец может отменить, причина обязательна, арендатора уведомить.
- v1.1: обе стороны могут отменить до подтверждённой передачи, а не до даты начала.
- Причина обязательна и для арендатора (базовое правило v1.0).

**Решено.** Q-5: владелец отменяет только в S2; в S3/S4 спор через поддержку. Замечание: в S3 у владельца нет действия для обращения в поддержку до перехода в S4 (TR-22 начинается с S4). Новое действие не добавлялось.

## A-7. Email (O-3)

**Есть.**
- Выбор отправителя: `Email:Provider == "Resend"` → `ResendEmailSender`, иначе `LoggingEmailSender` (`Infrastructure/.../ServiceCollectionExtensions.cs:80-83`, `EmailOptions.cs:21`). По умолчанию `Log`.
- Проверка готовности для верификации (`EmailVerificationSettings.IsOperational`, `:28-50`): Provider=Resend, ключ задан, `PublicBaseUrl` https. Иначе регистрация отвечает 503, а `EmailConfigurationStartupCheck` пишет Critical.
- Продакшен: `rental-api/docker-compose.production.yml:107-116` берёт `EMAIL_PROVIDER` из `.env`. В `rental-api/.env.production.example:97-130` значение пустое, с пометкой «в продакшене нужен Resend».
- По документам Resend включён с 2026-10-10: `knowledge/feature-notes/2026-10-10-email-verification.md:15` (домен подтверждён, трекинг выключен), `DEPLOY-PRODUCTION.md:1745-1754` (DKIM, SPF, DMARC p=none).
- Фактическая доставка по журналу деплоя **не проверена**: журнал есть только на сервере.
- Отправляются только верификация и сброс пароля (`Infrastructure/Services/EmailService.cs`, вызовы в `EmailVerificationService.cs:273`, `PasswordResetService.cs:143`). Письма о модерации только пишутся в лог (`EmailService.cs:24-56`). Писем по аренде нет.
- **Лимит на весь процесс** — `IEmailSendBudget` (`Application/Abstractions/IEmailVerificationSettings.cs:22-37`): по умолчанию 100 писем за 24 ч, «под квоту провайдера» (ADR-028 §8). Повторов и `Idempotency-Key` нет (ADR-029).

**Расхождение (C-11).** Письма по аренде (N-01, N-02, N-10, N-16) будут делить один лимит с верификацией и сбросом пароля. Когда лимит кончится, регистрация начнёт отвечать 503.

**Предложение (продукт).** AC-20. Чек-лист готовности, все пункты выполняет platform-engineer, продакшен в рамках этой задачи не трогается:
1. На сервере `EMAIL_PROVIDER=Resend` и ключ заданы. Последняя проверка «Delivered» по `DEPLOY-PRODUCTION.md:1972` записана в журнале деплоя.
2. Тариф и квота Resend покрывают ожидаемый объём писем по аренде. Лимит пересмотрен: отдельный бюджет или приоритет для писем аутентификации.
3. Письма по аренде отправляются только на подтверждённые адреса, с учётом языка профиля и отписки от несрочных.
4. Записан ADR о письмах по аренде (расширение ADR-028/029).

## A-8. Уведомления и системные строки чата

**Есть.** `Infrastructure/Services/NotificationEmitter.cs` — по аренде отправляются три вида:

| Метод | Строка | Ссылка |
|---|---|---|
| `BookingRequestedAsync` → владельцу | 31 | `/bookings/requests` |
| `BookingApprovedAsync` → арендатору | 55 | `/bookings/{id}` |
| `BookingDeclinedAsync` → арендатору | 79 | `/listings`; тело содержит сырую причину в кавычках, 88-90 |

- Плюс `PickupAreaChangedAsync` (168), единственный локализованный (`User.PreferredLanguage`, ADR-025).
- `NotificationKind` Confirm/Return/Review/Message и `NotificationCategory.Reminder` нигде не отправляются.
- Защиты от дублей нет: только `Guid.NewGuid()` и неуникальный индекс (`Infrastructure/.../NotificationConfiguration.cs:39-44`).
- Системные строки чата (`ChatSystemMessageEmitter.cs:18-21,37-47`): запрос, одобрение, передача, завершение.
  - Автора нет, `SenderId = null` (`ConversationsStore.cs:348`).
  - `LastMessageAt` обновляется (`:363`).
  - Защита от дублей — одна строка на (чат, вид), проверка перед вставкой (`:331-340`).
  - У отказа, отмены и истечения строк нет.

**Расхождение (C-10, C-17).**
- D-4 требует все виды на языке получателя. ADR-025 сознательно оставил английский.
- D-2 и AC-08 требуют строку с автором на каждое событие, а «одна строка на вид» не даёт повторяющихся событий: несколько предложений дат, несколько напоминаний.

**Предложение.**
- Продукт: матрица N-01…N-19 и RM-01…RM-09 v1.1 §13 и §5.
- Техн.: ключ дедупликации (аренда, вид, слот или событие); автор в системных строках; пересмотр ADR-025.

**Конфликт C-14 (ADR-044).** Полоса прогресса и таймлайн на странице брони (ADR-044, 18.10.2026, решение Тиграна) против карточки в чате без них (v1.0 §8). **Решено Q-12:** карточка заменяет полосу и таймлайн, когда чат заменит страницу брони; до этого ADR-044 действует. Поправка ADR-044 — при реализации.

## A-9. Поддержка, жалобы, доступ к чату (O-8)

**Есть.**
- Жалобы (`Domain/Entities/Report.cs`): цели Listing / User / Message, статусы Open / Resolved / Dismissed. Связи с бронью нет. Админ закрывает, отклоняет и переоткрывает (`AdminReportsController.cs:60,79,98`), с записью `ModerationLogEntry`.
- **Жалоба на Message указывает ID чата, а участие автора жалобы не проверяется** (`ReportsService.cs:145-152`: только `FindConversationByIdAsync`, затем подпись).
- Админ не может читать чат брони: `ChatService.IsParticipantAsync` (`:401-419`) пускает админа только в модерационные треды (`ConversationKind.Moderation`). Просмотр чатов админом не журналируется.
- Сущностей «обращение» и «спор» нет.

**Расхождение (C-08, безопасность).** Если сделать «жалоба открывает поддержке доступ к чату», любой, кто знает или угадает ID чата, сможет раскрыть админу чужую переписку.

**Предложение.**
- Продукт: обращение по аренде создаёт только её участник или система (AC-23). Доступ живёт ровно пока обращение открыто, журнал доступа хранится (§9.2).
- Техн.: отдельная сущность обращения, привязанная к брони. Проверка участия при создании. Проверка доступа админа на каждый запрос (обращение открыто), а не при открытии. Запись в журнал. Нынешние жалобы на сообщение отдельно проверить на тот же дефект и исправить (`/security-review`).

**Решено.** Q-10: переоткрывает только поддержка, с причиной; доступ к чату — пока обращение открыто. Q-20: при повторном закрытии поддержка может поменять итог (TR-34).

## A-10. Блокировка (O-12)

**Есть.**
- Вход запрещён (`AuthService.cs:183`). Refresh-токенов нет, JWT живёт 60 мин (`RentalPlatform.Api/appsettings.json:15`).
- Брони: любое действие отклоняется (`GetCurrentUserAsync`).
- Чат: нельзя создать чат и отправить сообщение, кроме обжалования в своём модерационном треде (`ChatService.cs:142,205,271`). Читать список чатов и переписку до истечения токена можно: в `GetConversations` и `GetConversation` нет проверки блокировки.
- `AdminUsersService.SuspendAsync` (`:177-195`) ставит `IsBlocked`, пишет журнал и модерационную заметку. Объявления и брони не трогает, обращений не создаёт (ADR-016, «Consequence still open»).
- Вторая сторона может продолжать действия по брони.

**Расхождение (C-09).** O-12 требует автоматическое обращение.

**Предложение.**

## A-11. Цена, период, минимум и максимум (O-5, O-6, B-2)

**Утверждённое правило (B-2, 19.10.2026).** День: N × цена за день; неделя: ceil(N / 7) × цена за неделю; месяц: ceil(N / 30) × цена за месяц; год: ceil(N / 365) × цена за год. N = max(1, возврат − начало) (ADR-043). Подробно в v1.1 §11.

**Есть.**
- Дни (ADR-043): `RentalPeriod.Days` = max(1, end − start) (`RentalPlatform.Domain/RentalPeriod.cs:10`). Его копия в интерфейсе — `countRentalDays` (`shared/utils/rental-days.utils.ts:11-14`). Обе считают одинаково, это основа для B-2.
- Быстрый выбор периода (`listing-booking-page.component.ts:57-62`): 1, 7, 30, 365 дней от сегодня. Кнопки совпадают с длинами периодов B-2. Кнопки короче минимума неактивны (`:249-251`). Занятые даты кнопки не учитывают. Других переключателей периода в интерфейсе нет.
- **Модель цены объявления:**
  - `Listing.PricePerDay` (decimal, `Domain/Entities/Listing.cs:12`) и `Listing.PriceUnit` (по умолчанию Daily, `:16`, `Infrastructure/Configurations/ListingConfiguration.cs:31-34`).
  - Введённое владельцем число уходит в `PricePerDay` при любой единице (`create-listing-form.component.ts:506-510,1241-1242`). Значит, колонка на деле хранит «цену за выбранную единицу», а не за день.
  - Форма редактирования использует ту же форму и единицу (`edit-listing-page.component.ts:151,219`).
- **Единица «час» доступна:**
  - в списке единиц интерфейса (`features/listings/models/create-listing.model.ts:9-17`, `PRICE_UNITS`);
  - сервер принимает её при создании и изменении (`[EnumDataType]` в `CreateListingRequest.cs:24` и `UpdateListingRequest.cs:21`; `ListingsOwnerService.cs:132,386`).
- **Расчёт суммы:** `TotalPrice = rentalDays * listing.PricePerDay` (`BookingsService.cs:117-136`, комментарий «assumes a per-DAY rate»). Предпросмотр в интерфейсе тоже умножает на дни (`listing-booking-page.component.ts:253-258`, `booking-calendar.component.ts:133-149`). Единица нигде не учитывается.
- **Показ цены:**
  - везде «за день»: карточка, страница игрушки, страница запроса, страница владельца;
  - модели интерфейса карточки и страницы игрушки не содержат `priceUnit`, хотя API его отдаёт (`ListingPreviewResponse.cs:12`, `ListingDetailsResponse.cs:11`);
  - единицу показывает только попап на карте (`listings-map-popup.component.ts:60-61`).
- **Бронь:**
  - хранит только `TotalPrice` (`Domain/Entities/Booking.cs:12`), без цены и единицы на момент брони;
  - ответы API брони содержат `PricePerDay`, взятый с текущего объявления (`BookingsService.cs:507,575`);
  - экраны брони показывают `TotalPrice`.
- **Минимальный срок:** `Listing.MinRentalDays` (int?, 1–365). Проверяется при создании (`BookingsService.cs:117-124`, `booking.below_min_rental`) и в интерфейсе (`listing-booking-page.component.ts:243-247`). При одобрении не проверяется.
- **Максимум 365** (`BookingsService.cs:15`). Проверяется только при создании (`:488-491`). В календаре нет `maxDate` (`booking-calendar.component.html:7`).
- В сид-данных единица не задаётся (`DependencyInjection/DevelopmentSeed/DevelopmentSeedData.cs`), то есть все объявления там посуточные. Цена за неделю, месяц, год и час встречается только в данных пользователей. Сколько таких объявлений на продакшене, неизвестно (запрос в документе миграции).

**Расхождение.**
- **C-02:** код не выполняет B-2. Объявление «7 000 ֏ за неделю» на 7 дней стоит 49 000 ֏ вместо 7 000 ֏, на 8 дней — 56 000 ֏ вместо 14 000 ֏.
- **C-20:** «час» доступен, а должен быть отключён для новых объявлений.
- **C-21:** нет снимка цены и единицы в брони. Пересчёт при изменении дат (§6) сейчас мог бы брать только текущую цену объявления. API брони показывает текущую цену, а не цену на момент брони.
- **C-22:** название `PricePerDay` и тексты («Price per day must be greater than zero», «What renters pay per day», ключ `myListings.ownerView.dailyRate.hint`) противоречат реальному смыслу.
- **C-23:** интерфейс не показывает единицу.
- **C-16:** при одобрении сроки не перепроверяются.
- Календарь даёт выбрать больше 365 дней, ошибку показывает только сервер.

**Предложение.**
- Продукт: v1.1 §11.1–§11.6, AC-26, AC-29…AC-32, тесты TC-P-01…TC-P-22.
- Техн. (рекомендации, не реализуются в этой задаче):
  1. Одна функция цены на сервере (рядом с `RentalPeriod`) и одна её копия в интерфейсе (рядом с `countRentalDays`). Обе прогоняют одну и ту же таблицу TC-P.
  2. Снимок в брони: цена периода и единица на момент создания (новые колонки). `TotalPrice` остаётся записанной суммой. Для старых броней снимок не заполняется, их суммы не пересчитываются (§11.5).
  3. Колонку `PricePerDay` не переименовывать в этой работе: это ломающее изменение API, поиска и админки. Зафиксировать в ADR, что это «цена за единицу `PriceUnit`», и исправить тексты.
  4. Не предлагать «час»: убрать из `PRICE_UNITS` для выбора, отклонять Hourly на сервере при создании и при смене единицы (новый код ошибки по ADR-045). Существующие значения в БД не трогать до решения M-K.
  5. Добавить `priceUnit` в модели интерфейса карточки и страницы игрушки, показывать единицу через общий помощник, как в попапе карты.
  6. Пересчёт при изменении дат — той же функцией по снимку.

**Решено.** Q-3 (срок проверяется при создании, принятии и изменении дат), Q-8 (снимок цены). Миграция: M-J (1), M-K (1)+(а), Q-15 (А) выбраны по делегированию, документ миграции §3.2.

## A-15. Отзывы (R-2)

**Есть.**
- Три вида: игрушка, владелец (их пишет арендатор), арендатор (пишет владелец).
- Условия: бронь Completed (`ReviewsService.cs:282`), правильная роль, по одному отзыву каждого вида.
- Срока нет, двойного слепого раскрытия нет, согласия нет.
- Чат закрывается, когда есть оба отзыва о людях (`ReviewsService.cs:323-337`, `ChatService.TryLazyCloseAsync`).
- ADR о правилах отзывов нет (упоминаются только в ADR-001).

**Утверждённое правило (B-1 вариант А, 19.10.2026).** Согласие владельца — «Получил обратно, закрыть аренду» (TR-17/18). Согласие арендатора — явное «Всё в порядке» (TR-23) или позднее «Всё было в порядке» (TR-32). Молчание согласием не считается. Отдельного действия согласия для владельца нет.

**Расхождение (C-01).** Код согласия не требует: отзыв доступен любой стороне сразу после Completed. Владелец закрывает аренду одним нажатием, арендатор не нажимает ничего (`BookingsService.CompleteAsync`).

**Расхождение (C-24).** D-9 описывает закрытие поддержкой с итогом T1 как «отзывы открыты», а по B-1 А согласие дают только стороны.

**Предложение (техн.).** Хранить в брони две отметки согласия (владельца и арендатора, с временем). `ReviewsService` проверяет обе, а не только статус Completed. Ошибка «отзывы ещё не открыты» — новый код по ADR-045.

**Решение (Q-16 A, 19.10.2026).** Итог T1 от поддержки отзывы не открывает. Они открываются по тем же двум отметкам согласия, что и без обращения; у арендатора остаётся TR-32. С предложением «две отметки согласия» это сходится: поддержка их не выставляет, поэтому закрытие обращения не требует отдельной логики отзывов. C-24 снят.

**Следствие.** Если владелец не нажимал «Получил обратно» до или во время обращения, после T1 отметки владельца нет, и отзывы закрыты навсегда. Это прямое следствие B-1 А и Q-16 A; решено Q-17: так и остаётся, TR-32 недоступен.

**Расхождение (C-25).** Сейчас чат закрывается только после обоих отзывов о людях, и ADR-001 это закрепляет (состояние `completed` = чат открыт). R-3 и Q-18 требуют «только для чтения» сразу при переходе в T1, T2 или T3.

**Предложение (техн.).** Блокировать отправку при переходе в итоговое состояние, а не в `TryLazyCloseAsync` после отзывов. Ошибка отправки в закрытый чат — по коду (ADR-045). Доступ поддержки при открытом обращении — отдельная проверка, не через участие. Сначала поправка ADR-001 (Rule 0).
