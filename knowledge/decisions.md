## ADR-001: Chat conversations are scoped to a Booking
Date: 2026-07-07 | Status: accepted
**Decision:** A `Conversation` is 1:1 (owner ↔ renter) and keyed to exactly one `Booking` (`BookingId` unique). The conversation's status pill is **derived** from the linked booking's status + a closed flag (requested→approved→active→return_due→closed), not stored. Per-participant read state (unread count, "Seen") lives in a `ConversationParticipant` row (`LastReadMessageId`/`LastReadAt`), one per user. Inbox-preview fields (`LastMessageAt`, snippet, toy title/image) are denormalised on `Conversation` for join-free list reads — same pattern as `Notification`.
**Why:** The approved DoRent design pins every thread to one toy+booking; system messages are emitted by booking lifecycle events; the read-only lock is "booking complete AND both reviews in". Booking is the natural key. Denormalising the preview + a participant read-cursor matches the codebase's existing join-free-read style and directly powers the unread badge and Seen receipt.
**Rejected:** (a) Conversation keyed by user-pair — breaks the design's per-booking system messages and status pill, and the existing Angular model already carries `listingTitle`. (b) Storing read state as two nullable columns on `Conversation` (OwnerLastReadAt/RenterLastReadAt) — simpler for strict 1:1 but doesn't generalise and reads awkwardly for the "Seen on my last message" query; the participant table is cleaner.
**Frontend impact:** the existing minimal Angular chat model (`title`/`participantName`/`listingTitle`/text-only) is replaced to match the design (booking-scoped, status, image/system messages). Contract rewrite handled by contract-guardian in a later Phase-1 increment.
**Amended 2026-07-11:** the pill vocabulary gained a `completed` state: requested → approved → active → return_due → **completed** → closed. `completed` = booking Completed but `ClosedAt` still null (chat open, awaiting both party reviews); `closed` is emitted ONLY from the `ClosedAt` override. Rationale: M-007's fix mapped Completed straight to `closed`, which made the pill read "Closed" on a conversation that still accepted messages — the vocabulary must distinguish "rental done" from "thread locked".

## ADR-002: Chat image attachments are served as unauthenticated capability URLs
Date: 2026-07-11 | Status: accepted (**deliberate trade-off, not an oversight**)
**Decision:** Chat attachments are written to a conversation-scoped directory with a server-generated filename and served by the same `UseStaticFiles` pipeline as listing images — i.e. **anyone holding the URL can fetch the file without being a participant, or even authenticated**. The URL is unguessable (GUID conversation path + GUID filename), so possession of the URL *is* the authorization ("capability URL").
**Why:** the human weighed it explicitly against the alternative below and chose to ship the vertical. It keeps the read path a plain `<img [src]>`, browser-cacheable, and identical in shape to listing images.
**Known consequence (accept it knowingly):** chat attachments are **private content between two users**, unlike listing images which are public by design. A URL that leaks — browser history, `Referer`, server logs, a forwarded screenshot — grants permanent, unrevocable access to that image. There is no participant check. `/security-review` will flag this; that finding is expected, and this ADR is the answer to it.
**Rejected:** an authenticated streaming endpoint (`GET api/chat/conversations/{id}/attachments/{file}`) that verifies the caller is a participant. Correct on privacy, but `<img src>` does not send the `Authorization` header, so the client would have to fetch each image as a blob and hand the component an object URL — more moving parts, no browser caching, and roughly half a day of extra work. Deferred, not dismissed: revisit before any real (non-demo) launch.
**Related infra:** `docker-compose.yml` mounts a `chat-uploads` volume at `/app/wwwroot/uploads/chat`; without it attachments vanish on image rebuild.

## ADR-003: Staging stand = single VPS + docker compose + Cloudflare Tunnel, one same-origin hostname
Date: 2026-07-13 | Status: accepted for the **infrastructure shape**, but the "staging stand" itself was **never deployed and never will be — see ADR-004**.
> ⚠️ `test.dorent.am` **does not exist** (NXDOMAIN; the tunnel has no route for it) and `docker-compose.staging.yml` has never been run. The VPS runs **production only**, on the apex — see the 2026-07-13 amendment at the bottom of this ADR. Everything about the *shape* (single VPS, docker compose, token Cloudflare Tunnel, same-origin nginx reverse proxy, zero inbound ports) held and went to production unchanged; only the word "staging" is fiction.
**Decision:** The test stand for `dorent.am` runs the whole stack (SQL Server, API, UI, cloudflared) via `rental-api/docker-compose.staging.yml` on one cheap VPS (Hetzner CPX12; the actual IP is deliberately not recorded here — this repo is public). Exposure is a token-based **Cloudflare Tunnel** (outbound-only; zero inbound ports, TLS by Cloudflare). One public hostname `test.dorent.am` → the UI's nginx, which already reverse-proxies `/api/`, `/uploads/`, `/hubs/` to the API container — same-origin, so **no CORS config and no API subdomain are required** (`api.dorent.am` is optional, Swagger convenience only). `ASPNETCORE_ENVIRONMENT` stays `Development` on the stand deliberately (dev seed + Swagger); secrets move to `.env`. Guide: `rental-api/DEPLOY-STAGING.md`.
**Why:** SQL Server (~2 GB RAM) rules out free tiers and Cloudflare Workers; the dev compose already models the full stack; the domain was already on Cloudflare, making the tunnel the shortest path to HTTPS with no nginx/certbot/ports on the host.
**Rejected:** (a) UI on Cloudflare Pages + API on VPS — splits origins, forcing CORS + a rebuilt `apiBaseUrl`, for no benefit at staging scale. (b) Azure App Service + Azure SQL — costlier and slower to set up for a throwaway stand. (c) Classic A-record + nginx/certbot on the host — works, but needs open 80/443 and cert management the tunnel gives for free.
**Amended 2026-07-13:** the same architecture went to **production**: `docker-compose.production.yml` (ASPNETCORE_ENVIRONMENT=Production — no seed/Swagger; admin via idempotent `Bootstrap__Admin*` bootstrap; api/ui healthchecks; log rotation), public hostnames `dorent.am` + `www` → ui:80 through tunnel `dorent-production`. The 2 GB VPS stays (no budget): 4 GB swap + `MSSQL_MEMORY_LIMIT_MB=1024` — acknowledged as temporary; rescale to 4 GB is the first upgrade when money allows. Daily backups: `deploy/backup-production.sh` (cron 03:30, 7-day retention, `--verify` restore test proven live). Off-site copy still pending. Classic A-record variant (c) was re-proposed by an external checklist and re-rejected — the tunnel already covers Full-strict-equivalent origin encryption with zero open ports.

## ADR-005: The production showcase owner uses the published `Demo1234` password
Date: 2026-07-16 | Status: accepted (**deliberate trade-off, chosen by the human after an explicit warning — not an oversight**)
**Decision:** production's demo catalogue is owned by `showcase@dorent.am`, a real, live, non-admin account on the public site, whose password is **`Demo1234`** — the same password documented in `CLAUDE.md` under "Demo accounts", in a **public** GitHub repo (`TTigSSar/rental-api`). Enabled via `Bootstrap__DemoContentEnabled=true` + `Bootstrap__DemoOwner*` in the server `.env`; the bootstrap creates the owner + the Approved seed listings/images and is idempotent/additive.
**Why:** Tigran wanted a memorable password he does not have to store or look up, weighed against the alternative below, and accepted the risk knowingly. The account is deliberately **not** an admin.
**Known consequence (accept it knowingly):** anyone can read the password in the public repo, and owner emails are visible around listings/conversations — so this account should be assumed compromisable by anyone who cares to try. Whoever holds it can edit or delete the showcase listings, approve/reject bookings made on them, and chat with real renters **as the platform's storefront**. There is **no lockout** on login and no password reset path on production (`IEmailService` is a development stub); login and registration *are* rate limited (policy `auth`, 5 requests/minute per IP, `RateLimiterExtensions`) - an earlier version of this line said there was no rate limiting at all, which was already untrue when it was written and was corrected 2026-09-25. `/security-review` will flag this; this ADR is the answer to that finding.
**Rejected:** a generated strong password written straight into the server `.env` (never through chat) and copied once into a password manager — objectively safer at near-zero cost, recommended by the orchestrator, declined by the human. Revisit before any real (non-demo) launch, together with ADR-002.
**Related:** demo content is otherwise clean — no other seeded accounts, no bookings/reviews/chats on production. Categories are NOT part of this trade-off: they ship as reference data via migration `20260716103601_SeedReferenceCategories` and exist regardless of the flag.

## ADR-004: There is no remote staging stand — local docker compose IS the test environment
Date: 2026-07-14 | Status: accepted
**Decision:** We do **not** run a remote staging/demo stand. The seeded test environment is the **local** `rental-api/docker-compose.yml` (ASPNETCORE_ENVIRONMENT=Development → idempotent dev seed + Swagger), which already models the full stack. `docker-compose.staging.yml` and `DEPLOY-STAGING.md` describe a stand that was never deployed; they are kept only as a starting point if a stand is ever funded, and are marked as not-deployed.
**Why:** the VPS is a 2 GB Hetzner CPX12 already running production, where SQL Server alone is capped at 1024 MB and a swap file is required merely to build images. A staging stand is a **second full stack including a second SQL Server (~1 GB)** — it does not fit. Deploying it on that box would very likely have the OOM killer take down the *production* database. It would also collide on ports (`127.0.0.1:8080` / `:4200` are already bound by production). The only safe variants cost money (a second VPS, or a rescale to 4 GB), and the stand is currently only needed by one developer who already has the identical stack running locally.
**Never do this:** do NOT "fix" an empty production database by enabling the dev seed there. Production is empty **by design** — `Program.cs` gates `SeedDevelopmentDataAsync()` behind `IsDevelopment()` and gives every other environment the idempotent `BootstrapAdminAsync` instead. The dev seed's accounts (`admin@rental.local` / `owner@rental.local`, password `Demo1234`) are **published in CLAUDE.md** and include an **admin**; seeding them into a live public domain hands over the admin panel to anyone who has read the repo.
**Rejected:** (a) second VPS (~€5/mo) — correct and fully isolated, revisit when a stand is actually needed by someone other than the developer; (b) rescale the current box to 4 GB (~€8/mo) — cheaper, but staging and production would share hardware, so a staging spike can still hurt production; (c) one SQL Server serving both a prod and a staging database — saves the ~1 GB but couples the production database to staging's load and migrations, which is worse than the problem it solves.
**How this bit us (2026-07-14):** ADR-003 read as though the stand existed, so an empty production database was diagnosed as "the seed didn't run" and the fix was nearly "add the missing DNS record for `test.dorent.am`". It resolves to NXDOMAIN because nobody ever deployed it. This is the M-001 class — a document describing intent was read as describing reality.

## ADR-006: Specialist subagent models — Sonnet by default, Opus only for platform-engineer
Date: 2026-07-19 | Status: accepted
**Decision:** Every specialist agent in `.claude/agents/` declares its model explicitly in frontmatter. `backend-dev`, `frontend-dev`, `contract-guardian`, `verifier`, `qa-engineer` → `sonnet`. `platform-engineer` → `opus`. No agent is left without a `model:` key. Opus for an implementation agent is now an explicit per-spawn override by the orchestrator (architectural work — store shape affecting several features, routing refactors), not a standing default.
**Why:** Claude Code's usage panel (2026-07-19) attributed **67% of a day's consumption to `frontend-dev` alone**, against 1% for `backend-dev` — the two agents do work of the same class, and the only difference was `model: opus` vs `model: sonnet`. `qa-engineer` and `platform-engineer` had **no `model:` key at all**, silently inheriting the orchestrator's Opus; harmless while their usage was ~2%, but a trap for the pending backups/monitoring work on dorent.am. `platform-engineer` keeps Opus deliberately: it is the only agent acting on live production (SSH, compose, backups, Cloudflare), where the cost of a wrong action is an outage, not a retry.
**Known consequence:** the claim "Sonnet is sufficient for Rental-Ui work" is a **hypothesis, not yet validated on this codebase**. If UI tasks start costing extra iterations or drifting from `Rental-Ui/CLAUDE.md` conventions, revert `frontend-dev` to Opus — and then look for the saving in session shape instead (see below), not in model choice.
**Rejected:** (a) leave everything on Opus — the workflow in `CLAUDE.md` §2 mandates subagents for all code, so ~100% of consumption flows through them; the model choice there *is* the cost model. (b) all-Sonnet including `platform-engineer` — saves little (it was ~2–3%) and spends the saving in exactly the place where a mistake is most expensive. (c) attack session length/context instead of models — real but secondary and behavioural, not configurable: the same panel showed 57% of weekly usage at >150k context and 56% from 8h+ sessions, addressed by `/clear` between unrelated tasks rather than by any file in this repo.
**Note on the figures:** the usage panel states they are approximate, cover local sessions on this machine only, and are independent characteristics rather than a partition — treat them as direction, not accounting.
**Amended 2026-10-07 (ADR-026, approved by Tigran):** the new read-only `reviewer` agent → `opus`. It runs rarely (contract/schema/multi-repo routes and security questions, not every change) and its job is authorization and ADR-conformance reasoning, where a miss ships to production. Every other assignment above is unchanged.

## ADR-007: Maps run on Leaflet + raster OpenStreetMap tiles, behind one `app-map` component
Date: 2026-07-21 | Status: accepted (**for Phase 1; the trilingual-label requirement is knowingly unmet — see below**)
**Decision:** The map stack is **Leaflet 1.9 with raster tiles from `https://tile.openstreetmap.org/{z}/{x}/{y}.png`**, no account, no API key, no style JSON. Leaflet is imported in exactly one file — `Rental-Ui/src/app/shared/ui/map/map.component.ts` (`app-map`) — via a dynamic `import('leaflet')`, with `leaflet.css` injected lazily as a `<link>` to `/leaflet/leaflet.css` (copied at build time by an `angular.json` assets entry, not bundled). Nothing else in the codebase may import Leaflet, and no Leaflet type crosses the component boundary: the public API is `center` / `zoom` / `pin` / `height` / `interactive` / `crosshair` / `circleRadiusMeters` in, `centerChange` / `mapError` out. The OSM attribution control is always visible — that is the ODbL license condition, not decoration.
**Why:** the approved design (`listing-location.jsx` in the claude.ai design project) is itself built on Leaflet + OSM raster, so this is 1:1 with what was signed off. Measured cost: **+4.27 kB** on the main bundle, with Leaflet itself in a separate lazy chunk (149.55 kB raw / 37.58 kB gzip) that loads only when a map actually mounts. Zero vendor accounts to create, zero keys to proxy, zero spend — and the exit is a one-URL swap because raster XYZ endpoints are interchangeable.
**Known consequence (accept it knowingly):** (a) **Trello card P0-3's trilingual-label requirement is not met.** OSM's standard raster style labels Yerevan in Armenian and Latin only — there is no Russian layer and no `coalesce(name:hy, name:ru, name)` expression, because raster tiles carry no queryable labels at all. RU-locale users see Armenian/Latin map labels. This is the price of skipping vector tiles and was accepted deliberately. (b) `tile.openstreetmap.org` is a **volunteer-funded service whose tile usage policy excludes heavy or commercial traffic**. At DoRent's current volume this is within fair use, and the detail page is tap-to-load specifically so a page view does not fetch tiles — but this stops being acceptable well before the platform is busy. Both are resolved by the same future move: MapLibre GL + a paid vector provider (MapTiler/Geoapify) with a versioned style JSON in the repo, which is what P0-3 originally specified.
**Rejected:** MapLibre GL + vector tiles now — it is the technically correct answer and the only one that delivers trilingual labels, but it needs a provider account, a key proxied through our API, a style JSON to own and maintain, and ~200 kB of library, for a Phase-1 slice whose job was to get two designed screens working. Deferred, not dismissed; revisit when either the label gap or the tile-policy limit actually bites.
**Amended 2026-07-22:** the tile-policy limit bit, sooner than expected. `tile.openstreetmap.org` started serving OSMF's **"418 Access blocked"** placeholder to this project's traffic — a white/yellow-striped PNG returned with a normal `200` and a valid image body, which is exactly the "excludes heavy/commercial traffic" risk flagged as a known consequence above. It was worse than a dead host: Leaflet's `tileload` fires on the placeholder the same as a real tile (valid 200, valid PNG), so the dead-tile-host detection wired up alongside this ADR (`822b2b2`) never triggered — the user saw a striped "broken" map, not the honest text fallback. Fix shipped: the tile URL template, attribution string, `maxZoom`, and API key moved out of the hardcoded constants in `map.component.ts` into `environment.tileProvider` (`src/environments/environment.ts` / `environment.prod.ts`), one config point for both environments. Default provider is now **MapTiler**'s raster endpoint (`https://api.maptiler.com/maps/streets-v2/{z}/{x}/{y}.png?key={key}`, free tier 100k tiles/month), with the attribution MapTiler's docs require verbatim: `© MapTiler © OpenStreetMap contributors` (linked to `maptiler.com/copyright` and `openstreetmap.org/copyright` respectively). The MapTiler account did not exist yet at fix time, so with `apiKey` empty `app-map` falls back to the same unauthenticated `tile.openstreetmap.org` endpoint and logs one console warning naming the config field to set — the app never ships a blank map for a missing key, but is also not actually off the throttled host until a real key is configured (see `Rental-Ui/CLAUDE.md` for how to set it). Placeholder-tile detection was reconsidered and deliberately left alone: no honest general heuristic was found for "every tile loaded but the map is unusable" — a check for suspiciously blank/uniform tiles would misfire on legitimate all-white or all-ocean tiles, and M-015's lesson (a check that misfires is worse than no check) argues against inventing one. **The trilingual-label gap from the original decision is still unmet.** MapTiler's `streets-v2` is also a raster style — it carries no queryable per-language labels, same as OSM's raster tiles — so RU-locale users still see Armenian/Latin map labels. Closing that gap still requires the MapLibre GL + vector-tile move this ADR has always deferred, not this swap.

**Amended 2026-07-24 (human decision, Tigran):** the listing-detail map's tap-to-load gate (`mapRequested` in `listing-location.component.ts`, added specifically because of this ADR's original "a page view must not fetch tiles" reasoning) is **removed**. The map now renders immediately whenever the listing has coordinates. This is safe specifically because of the 2026-07-22 amendment above: tiles now come from MapTiler with a real key, not raw `tile.openstreetmap.org` — a real quota (100k tiles/month on the free tier) with its own failure mode if exceeded, rather than an informal usage policy. The tradeoff was shown to the human explicitly before this change, and accepted knowingly: measured production tile traffic leaves comfortable headroom under that cap today, but a detail-page view no longer opts out of tile fetches the way it used to, so a future traffic increase could approach the quota in a way raw OSM's fair-use policy never gave a hard number for. If usage ever approaches the MapTiler cap, the options are: upgrade the MapTiler plan, or reintroduce a load-deferral (not necessarily tap-to-load — e.g. an intersection-observer-based lazy mount) — not silently re-add the button UX this amendment removes. The e2e journey in `e2e/listing-location.spec.ts` was updated to assert the new behaviour (tiles fetched on page load) instead of the old one (zero tiles until tapped).

## ADR-008: A listing's exact location is stored but never published — geohash-6 fuzzing is the public coordinate
Date: 2026-07-21 | Status: accepted
**Decision:** Three distinct location facts, three audiences.
- `Listings.Latitude`/`Longitude` — the exact pin the owner dropped. Visible to the **owner and admins only**.
- `Listings.PublicLatitude`/`PublicLongitude` — the **centroid of the geohash-6 cell** containing that pin, computed at write time. This is what every other caller receives, in the same `latitude`/`longitude` DTO fields. Measured cell size at Yerevan's latitude: **933 m east-west × 611 m north-south** (longitude cells narrow by cos(latitude); the textbook 1.22 km figure is equatorial).
- `Listings.DistrictId` — point-in-polygon of the exact pin against a committed OSM boundary asset. Public; district granularity is not sensitive.
`AddressLine` follows the **contact-reveal** gate instead: owner, admin, or a renter whose booking on that listing reached `Approved`/`Active`/`Completed` — the renter who is actually coming to collect the toy.
**Why:** these are family homes with children's toys. A raw coordinate is a reverse-geocodable home address, so the only safe design is one where the exact value never leaves the server for an unauthorized caller — not rounding at render time, not obscuring in the UI. Snapping at **write** time (rather than fuzzing per request) is what makes it hold up: every observer of a given listing sees the identical published point forever, so repeated or multi-account observation yields no additional bits and cannot be averaged back toward the truth. Two different exact points inside one cell publish identically. There is a test for exactly this.
**Consequences to respect:** (a) the detail map draws a **600 m** circle — deliberately not the design prototype's decorative 520 m — because a circle smaller than the real uncertainty claims precision we do not have, which is the failure this whole feature exists to prevent. (b) Any future distance filter, distance sort or map-pin endpoint (Phase 2, cards P2-1/P2-3) **must** compute from the public pair and round its output; computing a "rounded" distance from the exact pin re-leaks it through arithmetic. There are comments at the fuzzing seam saying so. (c) `latitude` in `ListingDetailsResponse` no longer means "where the toy is" — it means "where the toy is, to the precision you are entitled to". The frontend model documents this at the field; it is the most misuse-prone thing in the feature.
**Rejected:** (a) returning `null` coordinates to the public and showing no map — that was the H1 hotfix's interim state, and it makes the listing page strictly worse for renters who legitimately want to know the neighbourhood. (b) Per-request random jitter around the true point — trivially defeated by averaging repeated reads. (c) Publishing the district only, with no coordinates — safe, but loses the "roughly here in the district" information that makes the map worth showing at all.
**How this nearly bit us (2026-07-21):** the map, the fuzzing and the owner-facing promise ("only the approximate area is published, never your exact address", shipped in three languages) all went in while `AddressLine` was still being returned **ungated** to anonymous callers — the exact street address sat in the same JSON response as the deliberately-fuzzed coordinates. Card H1's own description asserted that field was already gated; it was not, and nobody checked, because the assertion sounded authoritative. Found only by an agent auditing adjacent code during the last card of the phase, and fixed in `875790f`. M-001 class: a document describing intent was read as describing reality.

**Amended 2026-07-25 (human decision, Tigran):** two changes, both product decisions made explicitly before implementation, not agent-driven scope creep.
1. **Geohash precision raised from 6 to 7** (`GeohashSnapper.Precision`): cell size at Yerevan's latitude goes from ~933m × 611m to ~117m × 153m. Driven by the radius filter below needing a public coordinate precise enough for a sub-kilometre ("0.2 km") search to mean anything — at the old ~933m cell, a 200m search radius was finer than the fuzzing itself, an incoherent combination. The snap-at-write-time invariant is unchanged (still no per-request jitter, still identical published pair for every point in a cell). Every already-populated `PublicLatitude`/`PublicLongitude` was computed at the old precision and needed a one-time re-snap: rather than reimplementing the geohash bit-interleaving algorithm a second time in SQL (which the code's own doc comments forbid — "there must never be a second place that decides how coarse the public pair is"), migration `InvalidatePublicCoordinatesForGeohashPrecisionUpgrade` just NULLs both columns for every listing with exact coordinates, and the pre-existing `ListingLocationBackfillRunner` (already run on every startup, already only fills nulls) recomputes them at the new precision on the very next startup — no new runner, no marker table, and the migration is schema-free (pure data, reviewed like `BackfillUsdListingsToAmd`).
2. **The distance filter (`ListingsQueryService`) now computes an actual Haversine circle, not a square bounding box, and does it against `PublicLatitude`/`PublicLongitude` — never the exact pair.** This reverses the 2026-07-24 feature note's "bbox is the accepted MVP shape, circle is a documented follow-up" and is deliberately still against the exact coordinate, even though computing from the exact pair would technically be "more accurate": filtering by the exact point turns the endpoint into a boolean in/out-of-radius oracle for an arbitrary caller-chosen circle — repeat with different centers and radii and you trilaterate the exact point, which is precisely the attack write-time snapping exists to prevent. It would also disagree with the detail page's map circle, which is drawn around the public point. The bbox is kept as a pre-filter (sargable range predicate the composite index can still use) with the Haversine refinement layered on top in the same SQL query — both stages translate to SQL Server (and to the SQLite test double) with no client-evaluation fallback; see `ListingsQueryServiceFilterTests` for the bbox-corner-but-outside-circle regression. `RadiusKm` is clamped to 0.2–20km rather than rejecting or taking out-of-range input literally.
3. **`ListingPreviewResponse` gained a nullable `DistanceKm`**, populated whenever the request supplies `OriginLat`/`OriginLng` (independent of whether a radius filter is also active), computed from the same public coordinate the filter uses — additive, contract-safe, and self-consistent with the filter by construction.


**Amended 2026-10-06 (superseded in part by ADR-024).** `Listings.Latitude`/`Longitude` is no longer "the exact pin the owner dropped" per listing — it is a **denormalised copy of that listing's owner's single home point**, shared by every listing they own. The three-audiences rule above is unchanged and is what ADR-024 builds on, but two things about it changed:
1. **The stakes are higher.** A leak of one exact pair now exposes the pickup address behind a person's *entire* catalogue, not one toy. The gating code and its tests were re-audited against this (`HomePointCoordinatePrivacyTests` serialises the real responses and substring-searches for the exact decimals, with a positive counter-test so a blank-everything regression cannot pass).
2. **There is a fourth location fact:** `Users.HomeLatitude`/`HomeLongitude` (exact, visible to that user themselves and admins only, reachable solely through `CurrentUserResponse.homePoint`), plus `Users.HomePublicLatitude`/`HomePublicLongitude` and `Users.HomeDistrictId` derived the same way as the listing columns.
Consequence (b) above — every distance filter, sort and pin computes from the public pair — is unchanged and now matters more, because the same public pair answers for all of an owner's listings.

## ADR-009: dorent.am is closed to the public by Cloudflare Access (email one-time code), not by anything on the server
Date: 2026-07-26 | Status: **SUPERSEDED by ADR-020 (2026-09-25). This decision was recorded as accepted and then never implemented** - the Access application was never created, so every word below describes an intention, not the stand. Verified anonymously from two vantage points on 2026-09-25: `https://dorent.am/` and `https://www.dorent.am/` return 200 with the app shell, `GET /api/categories` returns real JSON, and the server `.env` has no `CF_ACCESS_*` keys. `deploys.log` had already recorded it on 2026-07-31 ("Cloudflare Access NOT enabled ... smoke ran in PUBLIC mode") and twice on 2026-08-14. Kept in full as the runbook for closing the stand if that is ever wanted again; read it as a recipe, never as a description. See M-047.
**Decision:** The production stand is not publicly reachable. `dorent.am` and `www.dorent.am` — the whole surface, `/*`: SPA, `/api/`, `/uploads/`, `/hubs/` — sit behind a single Cloudflare **Access** self-hosted application (`dorent-production`) whose only human policy is `Allow / Emails / <owner>`, authenticated by a **one-time code sent to that email**. Session duration is **1 month** — a fixed dropdown, and at the time of writing its longest option short of "expires immediately"; if the dashboard ever offers longer, take it. A second policy, `Service Auth / Service Token dorent-smoke`, ordered **above** the email policy, lets `deploy/smoke.sh` through non-interactively. The gate lives entirely at Cloudflare's edge, in front of the tunnel: `docker-compose.production.yml`, `nginx.conf`, DNS and the tunnel itself are untouched, so both enabling and rolling this back are dashboard-only operations with no rebuild, no restart and no downtime. Runbook, verification and rollback: `rental-api/DEPLOY-PRODUCTION.md` section k.
**Why:** the requirement is "the owner can open the site from his PC and his phone, nobody else can" — an identity condition, not a network condition. Access is the only mechanism in the existing stack that expresses it directly: it is already part of the Cloudflare Zero Trust account that terminates the site's TLS and runs the tunnel (ADR-003), it costs nothing at this scale, and because it sits at the edge, a blocked request never reaches the 2 GB VPS at all. The device-independence requirement is what rules out every network-level answer.
**Consequences accepted knowingly:** (a) **A stolen or lost signed-in device keeps access for up to a month.** That is the price of not re-authenticating by email every day; the mitigation is manual and must actually be used — Zero Trust → My Team → Users → *Revoke user sessions* kills every session immediately. A shorter duration was rejected because the realistic outcome of daily email codes on a phone is that the owner starts looking for a way around the gate. (b) The `CF_Authorization` cookie is per-hostname, so `dorent.am` and `www.dorent.am` require separate logins. (c) Access now sits on the critical path of the live site: a Cloudflare Access outage or a mistaken policy edit takes the site down for the owner too — same blast radius the tunnel already has (ADR-003), not a new dependency. (d) Anything non-browser that ever needs the site — smoke checks today, uptime monitoring or an off-site backup pull later — needs its own service token; there is no anonymous path left. (e) The service token expires after a year and will present itself as `FAIL domain-*` in smoke.sh, with the remedy in the failure text.
**Rejected:** (a) **IP allowlist** (Cloudflare WAF rule, or Access policy with an IP selector) — rejected by the human, and correctly: the phone is on a mobile network with a dynamic IP, so the allowlist would have to be re-edited at unpredictable intervals, and the failure mode is the owner locked out of his own site with no self-service fix. It also grants access to *a network*, not to *a person* — anyone sharing that egress IP is inside. (b) **HTTP Basic auth in the ui container's nginx** — no Cloudflare account needed, but it edits `nginx.conf`, which is a contract with the app (M-008), it would have to be excluded for `/api/` and `/hubs/` or it breaks XHR and the SignalR WebSocket, credentials would live in a file on the box, and rotating them means a container rebuild. (c) **Taking the public hostnames off the tunnel and reaching the stand through an SSH tunnel to `127.0.0.1:4200`** — genuinely closed, free, and useless on a phone. (d) **Cloudflare Access with a Google/GitHub IdP instead of one-time PIN** — better UX per login, but adds an OAuth integration to configure and a second account to depend on, for a gate whose entire user population is one person.
**Side effect that had to be fixed in the same change:** `deploy/smoke.sh` checks the stand through its public domains, so Access would have turned every deploy's smoke check into a `FAIL` — and the workflow rule is that a deploy is not finished until smoke is clean. Disabling those checks was the wrong fix (it would delete exactly the checks that prove the public path works). Instead the script authenticates with the service token and derives its mode from the presence of `CF_ACCESS_CLIENT_ID`/`CF_ACCESS_CLIENT_SECRET` in `.env`. The check that earns the most is the new one: with **no** credentials, an anonymous request to both hostnames must NOT return the app shell — smoke.sh now re-proves on every single deploy that the gate is still closed, which is the one property nobody would otherwise notice silently regressing.

## ADR-010: `smoke.sh` may assert data invariants, not only liveness
Date: 2026-07-29 | Status: accepted
**Decision:** A deploy smoke check is allowed to assert properties of the *data*, in the **mandatory** tier, not only that processes answer. The first such check is `geo-map-pins`: it reads the approved-catalogue `totalCount` and the `map-pins` count, and fails when the catalogue is non-empty but zero pins come back. Any data assertion added under this ADR must carry a **discriminator** that separates "legitimately empty" from "broken" — here `totalCount` supplies the "there should have been something" — and must avoid thresholds pinned to product facts that move on their own.
**Why:** the geo surface fails silently by construction. Public coordinates are a *derived cache*: the exact point is authoritative, and `PublicLatitude`/`PublicLongitude` are recomputed by the startup `ListingLocationBackfillRunner`. If that backfill does not run, every listing stays healthy — it renders, it books, it answers 200 — while quietly vanishing from the map and from the radius filter. No liveness check can see that class of failure, because nothing is down. This was not hypothetical: the 2026-07-26 deploy ran a data migration that NULLs those columns and relies on the next startup to refill them, and `smoke.sh` would have reported 15/15 PASS with an empty map. The check was proven to work by pointing the real script at a loopback mock serving 12 listings and 0 pins on the production host: 18 other checks stayed green while this one failed — a direct measurement of the blind spot, not an argument about it.
**Consequences accepted knowingly:** (a) smoke.sh now has an opinion about data shape, so a deliberate product change (say, making coordinates mandatory, or emptying the catalogue) can redden a deploy that is technically fine — the cost of the check noticing anything at all. (b) The subset relation `pins ≤ totalCount` is only a **WARN**, not a FAIL: the two numbers come from two separate requests, so an approval landing between them violates it legitimately. A mandatory check containing a race is how checks lose trust, and a distrusted check is worse than a missing one (M-018). (c) `API_BASE` became overridable so the check is rehearsable against a mock; an overridden base is printed in every affected message, so a redirected run cannot be mistaken for a clean one.
**Rejected:** (a) **A warning tier for the geo check** — it would reproduce exactly the gap it closes: a deploy that broke the backfill would still exit 0, and nobody reads warnings on a green run. (b) **Strict `pins == totalCount`** — `Listing.Latitude`/`Longitude` are optional at create, so an approved listing without a map point is ordinary; this would redden on routine catalogue edits. (c) **A ratio floor** (e.g. "at least 80% of listings have pins") — same fragility, dressed as tolerance: the share of coordinate-less listings is a product fact that drifts, and the threshold would be re-tuned until someone silences it. (d) **Querying SQL Server directly from `smoke.sh`** — the most precise check available, and rejected because it would force the SA password into a script whose stated property is that it reads only two Access keys from `.env`; the HTTP endpoints prove the same invariant through the path users actually take. (e) **Leaving this to application tests** — unit and e2e tests run against fixtures and a stubbed or ephemeral database; the failure being guarded is a *production startup* not running, which by definition no test tier can observe.

## ADR-011: The DoRent brand mark is one component with a documented motion carve-out — and its resting frame is the animation's 0% keyframe
Date: 2026-07-29 | Status: accepted
**Decision:** The brand mark (orange ball + white wave, standing in for the "o" in "DoRent") is a single component, `app-ui-dorent-symbol` (`Rental-Ui/src/app/shared/ui/dorent-symbol/`), consumed by all three places that draw it: the desktop header brand (bounce on hover **and** keyboard focus), the new mobile app-open boot screen (`app-ui-boot-screen`, always animating), and the Home mobile guest topbar (static). It carries a squash-and-stretch bounce with a synchronized oval shadow. `DESIGN_RULES.md` §17, which lists "Bounce, spring overshoot" under **Prohibited**, was amended with an explicit carve-out naming this component and these two animated surfaces; the prohibition still governs UI chrome, cards, and content.
**Why the carve-out rather than silence:** the header already bounced before this change, so the rule was *already* false — a documented prohibition that the most visible element on every page violates teaches readers to stop trusting the document (M-001 class: a document describing intent read as describing reality). Naming the exception, and bounding it to one component and two surfaces, is what keeps the remaining prohibition enforceable.
**The load-bearing technical decision — rest state IS keyframe 0%:** the human's constraint was that the header at rest must stay exactly what it is today and that starting the animation must not be visible. That rules out swapping markup or classes on hover. So: one element, always mounted, always identical geometry; hover only starts a loop whose `0%`/`100%` frame is `translateY(0) scale(1,1)` — the rest transform. Two consequences fall out. (a) The shadow cannot take its opacity from the keyframes, because the loop's `0%` has the shadow at its *darkest* (ball on the ground), which would pop on the first frame — it is split into an outer `<g>` that fades opacity via a plain transition and an inner `<ellipse>` that runs the scale loop, so the opacities multiply. (b) The SVG is `viewBox="0 0 100 100"` sized exactly to the ball with `overflow: visible`, so the bounce and the shadow paint *outside* the layout box and nothing in the wordmark ever reflows.
**Consequences to respect:** (a) **Ink diameter equals the `size` input** — the circle is `r="50"`, filling the viewBox edge to edge on purpose. Optical kerning against the surrounding "D"/"Rent" is the **consumer's** job via `margin-inline`, not baked into the SVG. Shrinking `r` to "add breathing room" silently re-kerns every consumer; see M-024. (b) `clipPath` ids are per-instance (`dr-symbol-clip-N`) because three instances legitimately coexist on the mobile guest Home page. (c) The falling edge of the animation is deferred to `animationiteration` rather than removing the class immediately — measured in real Chromium, `transition: transform` does **not** ease an element home when a CSS animation is removed mid-flight; it snaps to identity on the very next frame. The deferral lets the loop ease itself back through its own rest keyframe first. (d) That deferral must never be the *only* path out of the animating state — see M-024.
**Rejected:** (a) **A shadow as a sibling DOM element**, as in the `jumping_ball.html` reference — it adds real height below the ball and pushes the wordmark's baseline around; drawing it inside the viewBox costs nothing and is layout-inert. (b) **A pre-Angular splash inlined in `index.html`** to cover the JS-download gap — it would be a fourth hand-maintained copy of the mark that by construction cannot reuse the component, defeating the point of the exercise. (c) **Boot screen on all viewports** — desktop boot resolves fast enough that the overlay would mostly flash and vanish; it is gated to ≤960px, the same breakpoint that already hides the desktop header. (d) **A "first time only" latch on the boot screen** — unnecessary: `AuthState.isInitializing` is set true only in the initial state and every reducer case only ever sets it false (there is already a regression test that logout must not restore it), so it cannot re-fire mid-session. Verified rather than assumed.

## ADR-012: The catalogue map fetches by viewport, renders its popups in Angular, and clusters on exact coordinate equality
Date: 2026-08-01 | Status: accepted
**Decision:** `/listings` gained a List/Map toggle (`?view=map`) whose map draws every matching listing as a 150 m uncertainty circle with the brand ball (ADR-011) at its centre, fed by `GET /api/listings/map-pins`. Four decisions inside that are load-bearing and none of them is the obvious one.

**1. Pins are re-fetched per map viewport, not once per filter — and the auto-fit that follows a fetch must not feed itself.** `map-pins` caps at 500 rows (newest first) and reports `isTruncated`; with a single filter-scoped request a broad filter silently hides listings, and the user has no way to reach them. Sending `minLat/maxLat/minLng/maxLng` on every `moveend` (debounced 400 ms, `switchMap` in the effect so stale viewports cancel) keeps the count naturally bounded, so the cap is practically unreachable and "everything in this area" is true rather than approximately true. The hazard this creates is a feedback loop — fetch → auto-fit the map to the results → `moveend` → fetch — and it needs **both** halves of the guard to stop: (a) auto-fit runs only for the response to a `bounds: null` request, i.e. initial open and filter change, never for a viewport-driven response; (b) `MapComponent` does not emit `viewportChanged` for a move it caused itself via `fitBounds`, because it is the only thing that knows it initiated that move. Either half alone still spins.

**2. The popup is an Angular component projected into a new `[app-map-overlay]` slot, not `L.popup`.** Leaflet's popup takes an HTML string. The content needed here is a `routerLink`, ngx-translate keys, an image, the rating block reused verbatim from `listing-card`, and — for coincident listings — a vertical stack of N of those. Feeding that through `L.popup` means either a second, hand-written rendering path for markup Angular already owns, or interpolating listing-controlled titles into an HTML string, which is an XSS sink by construction (any registered user can name a listing). The cost accepted instead: the parent has to position the popup itself, so `MapComponent` gained `markerHovered` emitting a **container-pixel anchor**, re-emitted on `move`/`zoom` while a popup is open so it stays glued during a pan. That output therefore doubles as an anchor-update channel and is not purely a hover signal.

**3. Coincident listings are grouped by exact coordinate equality, and that is exact rather than a heuristic.** Write-time geohash-7 snapping plus `decimal(9,6)` storage means two listings whose real addresses fall in the same ~117 × 153 m cell publish **byte-identical** coordinates, so `` `${lat.toFixed(6)},${lng.toFixed(6)}` `` is a sound cluster key, not a proximity guess. One circle, one ball, one badge; hover opens every pin's card in a scrollable stack. **Known limit, deliberately not solved:** two neighbouring addresses that straddle a cell boundary publish centroids 117–153 m apart and stay two circles. Pixel-distance clustering (`leaflet.markercluster` or hand-rolled) was rejected for this iteration — it adds a dependency and a zoom-dependent identity for a group, which the popup stack and the count badge would then have to track; exact-equality grouping has a stable key at every zoom.

**4. Balls are static and bounce only while hovered — the inversion of the original brief.** The brief asked for all balls bouncing continuously, stopping on hover. Rejected on two grounds: up to 500 simultaneously animating SVG markers is a real cost on a mid-range phone, and a map where every element is moving is unreadable — the motion carries no information when it is everywhere. Tigran chose the inversion, which also lands the map on the same gesture as the header brand: the ball bounces where the pointer is.

**Consequences accepted knowingly:** (a) `map-pins` is `[AllowAnonymous]` and unthrottled, and now receives a request per debounced pan rather than one per search. The security review found no new information leak — the bounding box filters on, and the response returns, the *same* fuzzed pair, so shrinking the viewport can only include or exclude a point whose published value the caller already has, which is why this does not reopen the trilateration oracle ADR-008's amendment closed. The traffic profile did change; if that becomes a problem it is a rate-limiting question, not a privacy one. (b) `ListingMapPinResponse` gained `Rating`/`ReviewCount`, so the per-row `ToyReviews` aggregate subquery now runs on up to 500 rows instead of a page of 20–100 — the same shape, the largest row count in the codebase running it. (c) `?view=map` lives in the URL so the view is shareable, but is parsed **separately from `ListingsFilter`** — anything inside that model reaches `buildListingsQueryParams()` and is sent to the backend, and a view mode has no business there.

**The brand ball is shared as a Sass mixin plus a markup function, not by reusing the component** — this is the one place ADR-011's "single component owns the mark" had to bend. `DorentSymbolComponent` is `ViewEncapsulation.Emulated`, so its compiled CSS carries `_ngcontent` attributes and cannot style raw HTML handed to a Leaflet `divIcon`; `MapComponent` is `ViewEncapsulation.None` precisely so its marker CSS is global. The rest state, keyframes and reduced-motion block therefore live in `_dorent-symbol-motion.scss` as a mixin parameterised by the "currently animating" selector, included by both stylesheets, and the SVG lives in `dorent-symbol.markup.ts` behind a function taking a per-marker `clipPath` id (a shared id breaks the white wave on every pin). Identical `@keyframes` emitted twice is harmless. **Copy-pasting the keyframes was rejected** as two sources that would silently diverge, and **promoting the symbol's CSS to global** was rejected as a larger blast radius on the app's most visible element for a single new consumer. The unavoidable cost: M-024's reduced-motion latch had to be re-solved independently in `map.component.ts` — a class cleared only on `animationiteration` never clears under `prefers-reduced-motion: reduce` — and it has its own regression test there.

**Amendment 2026-08-03 — the circle is 100 m, not 150 m.** The uncertainty radius was tightened on Tigran's call; the number lives in exactly one place, `APPROXIMATE_AREA_RADIUS_METERS` (`Rental-Ui/src/app/features/listings/models/approximate-area.const.ts`), which both this map and the listing-detail block read, and which the "~N m" pill interpolates. What did **not** change is the floor it must clear: the geohash-7 centroid-to-corner worst case is ~96.3 m, so 100 m leaves only ~3.7 m of headroom where 150 m left ~54 m. The constant can no longer absorb a precision change silently — if `GeohashSnapper.Precision` moves, recompute the half-diagonal and raise the constant in the same change, or the map starts claiming precision the backend does not withhold.

**Rejected:** (a) **A single filter-scoped request with a "narrow your filter" banner at 500** — simpler, no debounce, no loop hazard, and rejected because it makes the map quietly incomplete exactly when the catalogue grows, which is the moment a map earns its keep. The `isTruncated` banner is still wired as a backstop. (b) **A split list+map layout** (grid left, sticky map right) — rejected in favour of the toggle: it needs two-way hover synchronisation between card and pin, and it squeezes the results grid to two columns on the desktop widths this catalogue targets. (c) **Drawing the active radius/origin circle from `radius-origin-filter` on this map** — genuinely useful and deliberately deferred; it is a follow-up, not a gap.


**Amended 2026-10-06 (ADR-024).** Clustering by exact equality of the snapped pair now has a much stronger effect than the "two neighbouring addresses that straddle a cell boundary stay two circles" limit described above: **every listing of every multi-listing owner is always a single cluster**, by construction, because they all carry the same public pair. That is a consequence of the home-point model, not a clustering change — but it means the pin count on the map is now "owners with listings in view", not "listings in view", and a dense owner no longer spreads across a district. The 100 m uncertainty circle (`APPROXIMATE_AREA_RADIUS_METERS`) and its coupling to geohash-7 are unchanged.

## ADR-013: A booking request carries a renter's note, and the owner reads it while the request is still Pending — but sending one still unlocks nothing
Date: 2026-08-05 | Area: backend + frontend (booking flow)

The `Item & Booking` design makes a free-text note the centrepiece of the booking page: the renter writes to the owner, sees a live preview of the chat bubble the owner will get, and the owner reads it on the request card while deciding. The UI for all of that already existed — textarea, suggestion chips, preview — and `onSubmit()` threw the value away behind `// TODO: wire noteForOwner to API when backend supports notes`. The backend had no field.

**`Booking.Note` is `string?`, max 280, set once at creation and immutable** — no edit endpoint. It is trimmed before the length is judged (so trailing whitespace cannot push a borderline note over), and whitespace-only is stored as `null` rather than `""`, so "no note" has exactly one representation. Over-length is rejected in `BookingsService` as `booking.note_too_long` rather than by a `[MaxLength]` attribute, because the attribute would validate the *untrimmed* string and disagree with what gets stored.

**The note is deliberately NOT gated by booking status.** Every other renter/owner-private field on a booking (phone, address) is gated to `Approved`/`Active`/`Completed`. The note is the exception on purpose: the owner needs it *while the booking is Pending*, because it exists to inform the accept/decline decision. Gating it would make the field pointless. It rides on `BookingRequestResponse` (owner-scoped query) and `BookingDetailResponse` (both parties, behind the existing authorization check) and reaches no anonymous or public endpoint.

**The design's "phone unlocks right after you send" was rejected.** The server reveals contact only at `Approved`+, and the listing-detail page already said so — the booking page contradicted it, promising the number on send. Adopting the design would mean any renter can unlock any owner's phone number with a request that costs nothing and expires in 24 hours. Instead the **copy was corrected to match the server** on both pages, and the confirmation offers **"Message the owner"** — which opens the real booking-scoped chat thread via the previously-uncalled `ChatApiService.getOrCreateFromBooking`. That is a genuinely unlocked channel, so the screen still delivers an immediate way to reach the owner without turning a free action into a contact-harvesting primitive.

**Consequence worth knowing:** chat conversations are strictly booking-scoped server-side (`from-booking/{bookingId}` is the only creation path), so pre-booking chat does not exist. The details page's "Message owner" therefore routes to the owner's public profile, while the confirmation's routes to a real thread. The two buttons share a label and do different things — that asymmetry is forced by the backend, not a design slip.

**Rejected:** (a) **Revealing on `Pending`** — above. (b) **Adding the note to `BookingResponse`** (the create response and `/bookings/mine`) — the renter already knows what they typed; two read paths were enough. (c) **A service fee line** in the price breakdown, which the design shows — that is a pricing/business decision with billing consequences, not a UI one. The **refundable deposit** line was added instead, from the `depositAmount` the listing already carries, marked as not charged now and **excluded from the total**. *(Superseded 2026-09-17 by ADR-018: that line is now "Loss & damage compensation", still excluded from the total.)*

**Amended 2026-09-14 — the phone reveal is gone; chat replaced it.** This ADR's central mechanism, "the server reveals contact only at `Approved`+", no longer exists. `ListingOwnerResponse.PhoneNumber` and `BookingDetailResponse.CounterpartyPhoneNumber` were deleted, so **no endpoint returns another user's phone number** to a renter or an owner, at any booking status. The four padlock notices that existed to explain the wait now read as chat notices instead.

**Why the mechanism became redundant rather than merely unpopular:** this ADR already recorded that chat is strictly booking-scoped (`from-booking/{bookingId}` is the only creation path). That fact, written down here as a *limitation*, is the whole feature. It means "a renter can reach an owner only after a rental request exists" is enforced by the schema, not by copy — which is exactly the property the `Approved` gate was protecting. Once chat existed, the platform-mediated reveal was a second, worse answer to a question already answered: worse because the platform handed the number over automatically, where chat lets the renter **ask** and the owner **choose**. Consent beats a status gate. Tigran's call.

**One loosening, accepted knowingly:** chat opens at `Pending`, whereas the phone unlocked at `Approved`. So the renter reaches the owner one status earlier than before — but reaches a message thread, not a phone number, and the owner can simply not reply. This is the intended rule ("message the owner only after a rental request"), not an oversight.

**What survived:** the pickup **`AddressLine`** is still gated to `Approved`+ — `ContactRevealed` in `ListingsQueryService` and `contactRevealed` in `BookingsService` are kept for it and now document that single purpose. Phone is still **collected** at registration, still shown to the user on their own profile, and still drives the `IsPhoneConfirmed` trust badge; only the cross-user reveal is gone. `User.PhoneNumber` was untouched — **no migration**.

**The deliberate exception: admins.** `AdminUserSummaryResponse.PhoneNumber` and `AdminListingDetailResponse.OwnerPhoneNumber` were added so moderators can call a member. Both ride endpoints already carrying `[Authorize(Roles = "Admin")]`, and `OwnerPhoneNumber` is on the inspect **detail** DTO only — not the summary or pending-review DTOs, so it never reaches the queue lists. Rendered as `tel:` links in the admin user dialog, the users page and the owner trust panel.

**Net effect on the security posture: strictly narrower.** The old rule let any renter unlock any owner's number by getting one booking approved; there is now no API path to another user's phone outside the admin role. The regression is pinned from both directions — `ListingOwnerPhoneNotExposedTests` asserts `phoneNumber` never appears in the listing-detail JSON at any booking status, and `e2e/listing-contact-privacy.spec.ts` was strengthened rather than retired.

## ADR-014: The design is the source of truth for form; the backend is the source of truth for claims
Date: 2026-08-05 | Area: process (design → implementation)

*Applied again in ADR-018 (2026-09-17), which removed the "refundable deposit" claim itself and excluded the compensation design's unbacked copy.*

Implementing the `Item & Booking` design surfaced a recurring class of block: visually specified, structurally sound, and backed by no data the platform actually has. Rather than decide ad hoc each time, the rule applied throughout was: **a design mock specifies layout, hierarchy and treatment; it does not license a factual claim the backend cannot substantiate.** Where the two conflict, the block is dropped and the omission reported — never filled with a plausible constant.

Dropped on that basis, each with the reason: **"What's included"** (no `Listing.Inclusions` field), **related/nearby listings** (no similar-listings endpoint that excludes the current listing), **"Booked 3 times this week"** (no booking-frequency data), **owner "Reply rate 98% / Replies in <2h"** (`ResponseRate` is declared on `PublicUserProfileResponse` and hardcoded `null`), **review "Helpful (n)"** (no column), and **"Free cancellation up to 24h"** (no such policy exists server-side). Two of the design's five **protection bullets** went the same way: they described a deposit damage-claim and automatic-refund process, and DoRent runs no claims, disputes or refunds — deposits are exchanged directly between owner and renter, off-platform.

The same rule cuts the other way and is the more useful half: blocks whose data **already existed and was being discarded** got built. The details page was fetching `ToyReviewSummary` and throwing away `distribution` and all five per-criterion averages; the design's rating-distribution bars needed no backend work at all. Note the gate that matters there — `ReviewsService.MinReviewsForAggregate = 2`, and below two reviews the API still returns `0.0` averages, so rendering unguarded would print a fabricated 0.0. `hasAggregate` is the flag; the empty state is the honest render.

This is M-027's rule ("dropping an API's uncertainty field renders a guess as a fact") generalised one step: **a number with no source is worse than a missing block, because the missing block is visibly missing and the number is not.** The practical protocol: when a design block has no data behind it, raise it with the human as a scope question — add the backend field, or drop the block — and record which was chosen. Do not let the implementing agent resolve it silently, because the cheapest resolution at that moment is always a plausible-looking constant.

## ADR-015: A design mock specifies pixels, not permission flows or licence chrome — the hero map is opt-in, and its badge moved
Date: 2026-08-11 | Area: frontend / Home hero map (design → implementation)

The `DoRent Home` design specifies a hero map: a 460×330 panel with a radius circle, twinkling pins, a blue "my location" dot, and a bottom-left "N toys nearby" badge. Built literally, that mock produced two defects — and neither is a drafting error. Both are things a static mock is structurally incapable of expressing, so both will recur on the next map surface unless the rule is written down.

**1. The mock shows a located user, so the first implementation asked for location on load.** Home is the landing page, so every visitor got an unsolicited permission prompt before doing anything. `/code-review` and `/security-review` arrived at the same root cause from different directions: a browser stores a "Block" **per origin**, so a visitor declining a prompt they never asked for permanently disabled the `/listings` radius filter's own "use my location" — previously the only feature that ever prompted — and, for everyone who allowed, precise coordinates began landing in backend access logs via the `originLat`/`originLng` query params for the bulk of all traffic rather than for the few who deliberately used a radius search.

**Decision: the hero map defaults to a Yerevan-centred fallback and never calls `GeolocationService` on init.** Location is opt-in behind a button on the panel itself. Rejected: prompting on load (matches the mock most literally, accepts both consequences) and silently reusing an already-granted permission via the Permissions API (better, but still makes an unrelated page's decision govern this one). A permission is a **shared, single-use, origin-wide resource**; spending it is never a local decision by whichever page happens to load first.

Two consequences worth carrying: the state that models this is named `useFallbackOrigin`/`isFallback`, **not** `originDenied` — nothing is denied when nothing was asked, and a state name that misdescribes reality is how the next reader gets misled. And outbound coordinates are rounded to 3 decimals (~100 m) while the **displayed** dot keeps full precision: the backend already publishes pins at geohash-7 centroid resolution, so full precision in a query string buys a decorative badge nothing and costs log exposure.

**2. The badge's specified position was unsafe, because the mock drew tiles nobody has to pay for.** The design places the "N toys nearby" pill bottom-left. The app's real map renders the MapTiler logo bottom-left and Leaflet's attribution bottom-right — both **licence-required**. The design used raw OSM tiles with no logo, so its bottom-left corner was genuinely free and the collision could not have appeared in the mock. The pill moved to top-left, which is free on this map specifically because the zoom stack only renders when `interactive` is true and the hero map is frozen.

**The rule:** a design mock is authoritative for layout, hierarchy and treatment (ADR-014), and it is authoritative for **nothing that only exists at runtime** — permission prompts and their persistence, licence chrome, empty and error states, or any state the mock had no way to draw. When a mock implies one of these, treat it as a scope question for the human, not as a specification. The tell is that the mock shows a *result* (a located user, a clear corner) without showing the *transaction* that produces it.

**Corollary on counts.** The fallback branch counts a ~10×13 km citywide box; the granted branch counts a 1.2 km radius. Rendering both through the mock's single "{{count}} toys nearby" string made two numbers an order of magnitude apart claim the same thing. They now use separate keys (`nearbyCount` / `cityCount`). This is ADR-014's rule applied to copy: **one string, two meanings, is the same defect as one number, no source.**


**Amended 2026-10-06 (ADR-024).** Two additions, both deliberate.
1. **One accepted exception to "an origin travels only when the user asked for it":** the home page's hero map ("Toys near your home") sends the signed-in user's home point, rounded to 3 decimals, with the default nearby radius, on every load — no radius picked by the user. Tigran accepted this explicitly: the map cannot be centred on a home without it, the value is coarser than the ~100 m public cell, and the server already stores the exact point. The catalogue keeps the stricter rule — nothing is sent until a radius is chosen.
2. **The rounding seam moved and is now the only one.** `roundCoordForApi` lives in `shared/utils/coord-precision.utils.ts` and is applied in `buildSharedFilterParams`, through which all three origin producers (home point, live geolocation, manual pick) pass. Callers hand over full precision deliberately — the local blue dot needs it — and only the request is coarsened.
**Known exception that is NOT covered by the rounding rule:** `GET /api/districts/at` sends the candidate home coordinate at full precision **in the query string**, so it reaches access and Cloudflare logs, including during sign-up. Raised as a Medium security finding and accepted as-is by Tigran (see ADR-024). It is the one place in the home-point feature where this ADR's own rule is knowingly not met; rounding it was rejected because a 3-decimal (~110 m) round can flip the resolved district near a boundary and make the picker's chip disagree with what the write side accepts.

## ADR-016: The admin console owns its own chrome, hiding a category retires the label not the inventory, and the "needs category fix" flag is a seeded keyword table
Date: 2026-08-14 | Area: backend + frontend (admin console redesign)

The `Admin.html` design replaced a single moderation page (`/admin/listings/pending` — a mobile card list with a reject bottom sheet) with a six-screen console: Overview, Listing review, Item inspect, Categories, Users, Reports & flags. Four decisions inside it are load-bearing, and the code does not explain any of them.

**1. Inside `/admin/**` the app's global chrome is suppressed and the console draws its own.** The design's console has a 64px top bar and a 244px left rail on desktop, and its own five-tab bottom nav on mobile — all of which would have stacked on top of the app's existing `app-header`, footer, and three-item admin bottom nav. `isAdminConsolePage()` in `app.ts` folds into the existing `showFooter`/`showBottomNav` predicates rather than adding a parallel mechanism, and `<p-toast>` stays mounted because the console's optimistic mutations depend on it. The consequence to respect: **the admin area is now the only part of the app that does not inherit global chrome**, so anything added to the header or bottom nav in future is invisible to moderators unless it is also added to the console shell. `/admin/listings/pending` survives as a redirect because the admin bottom-nav link and any bookmark still point at it.

**2. Hiding a category retires the label, not the inventory — and that was the human's explicit call, against the first implementation.** The backend initially filtered hidden-category listings out of every public discovery surface: the category list, unfiltered browse, search, map pins, and the home sections. Tigran chose the narrower reading. Final behaviour: the category disappears from `GET /api/categories` and an explicit `categoryId` filter on it returns nothing, **but its listings remain in general browse, search, map pins, and every home carousel**. So `IsVisible` is a *taxonomy* control, not a takedown switch — a moderator retiring "Party Toys" removes a browsing label and strands no owner's inventory. The check therefore lives in exactly two places (`CategoriesQueryService`, and the `CategoryId.HasValue` branch of `ListingsQueryService.BuildApprovedListingsQuery`, which is shared by the paged search and the map-pins endpoint) and deliberately **not** in `HomeSectionsQueryService`. The four cases are pinned by `CategoryVisibilityPublicTests`; without those tests the narrow reading is one plausible-looking `&&` away from silently becoming the broad one.

**3. The "Needs category fix" flag is a deterministic keyword table, chosen over both a heuristic and nothing.** The design shows a badge and a one-click Apply comparing the owner's category against a server-suggested one; no such signal existed. Three options were put to the human: invent nothing and ship only the manual recategorise control, invent a fuzzy/ML matcher, or build an explicit rule a human can read. The choice was the rule: `CategoryKeyword` (seeded, no admin CRUD yet), whole-word case-insensitive matching via `(?<![\p{L}\p{N}])…(?![\p{L}\p{N}])` rather than `\b` so multi-word and hyphenated keywords like `"balance bike"` and `"ride-on"` still match at string edges, **presence-per-field** scoring (title 3, description 1) so keyword-stuffing a description cannot inflate a score, ties broken by `DisplayOrder` then `Id` so a listing never flip-flops between page loads, and suggestions computed **only** for `PendingApproval` listings so an approved listing is settled and does not nag. The seed deliberately excludes generic words ("wooden", "toy", "kids") that appear in nearly every listing — a flag that fires on everything is worse than no flag. This is ADR-014's rule satisfied rather than bent: the badge makes a factual claim, and now something substantiates it.

**4. Four design blocks were dropped for want of a backend, and one derived rather than invented.** Dropped: the post-decision **Undo** (there is no un-approve endpoint — a successful decision navigates back with a toast instead of offering a button that cannot work), the **"notify the owner I changed the category" toggle and note composer** (`PATCH .../category` takes only `categoryId`), **"Message owner"** on the inspect dossier (chat is booking-scoped and an admin has no booking — it links to the owner's public profile instead), and the detail dialog's static **"suggested steps to resolve" playbook** (flavour text tied to no data). Derived rather than invented: the design's **compliance checklist** (`checks: {photos, safety, hygiene}`) has no backend equivalent, so it is computed client-side by one shared unit-tested function — `photoCount >= 3`, `safetyNotes` present with an age range, `hygieneNotes` present — with the thresholds confirmed by the human rather than chosen by an agent.

**Consequence still open at close:** suspending a user cuts their access *immediately* — `EnsureAdminAsync` re-reads the user on every admin call and rejects on `IsBlocked`, so even a valid JWT stops working — but **nothing cascades to their inventory**: an approved listing stays public and bookable, and in-flight bookings keep their status. That is an accepted gap awaiting a product decision, not an oversight; it is recorded here so the next person to read `suspend` does not assume it is a takedown.

**Rejected:** (a) **Building only the review queue** and leaving the other five screens as stubs — the human chose the full console explicitly. (b) **Desktop-only**, which the design's own handoff note recommends — rejected because DoRent is mobile-first and the design itself ships 390px screens for every surface. (c) **Filtering hidden categories out of all discovery** — see 2. (d) **Regenerating a category's slug on rename** — `HomeSectionsQueryService` hardcodes `"baby-toys"`/`"outdoor-toys"` and the frontend keys a visual lookup off the slug, so renaming would silently break two home carousels; slug is fixed at creation.

## ADR-017: Delivery is multi-select via an additive flags column; the owner no longer types a street address
Date: 2026-09-15 | Area: backend + frontend (create-listing wizard, step 3)

The owner asked for "How can renters get the toy?" to allow both Pickup and Courier. `DeliveryType` had been deliberately modelled as a single nullable enum ("single-select by design", per its old comment), so this reverses that decision.

**1. Storage and contract are additive, not a replacement.** A new `[Flags] DeliveryOptions` column (`Pickup = 1`, `Courier = 2`) is the source of truth. The migration `AddListingDeliveryOptions` backfills it from `DeliveryType` (0→1, 1→2). The API gains `deliveryTypes: ("Pickup"|"Courier")[] | null` on the create/update requests and on the details and my-listings responses. The legacy scalar `deliveryType` is kept on all four and **mirrored**: Pickup if the set includes Pickup, else Courier. `DeliveryOptionsMapper` (Application/Common) is the only place the two representations convert, so the write path and read paths can't drift. On update, null means unchanged and `[]` is a 400. Delivery is a structured field, so changing it never re-triggers moderation. The details query expands the flags after materialization, because the expansion isn't SQL-translatable. That is why `ListingDetailsResponse.DeliveryTypes` is `set` rather than `init`.

**2. The street-address input was removed from the wizard.** The pickup location is now only the map pin, via "Show on map", which opens the existing picker. The inline map preview is gone too. The create payload sends `addressLine: null`. Update never touched `AddressLine`, so existing addresses survive edits. **Consequence to respect:** new listings have no street address for the approved-renter reveal in `ListingsQueryService`. The handover is arranged via the exact pin (visible to the owner) and booking chat. The `AddressLine` column and its gating stay in place in case the field comes back.

**3. Minimum rental gained 30/90/180/365 days** within the existing `[Range(1, 365)]`, so there was no backend change. The eight chips get their own full-width row, one line from 1024px up and wrapping below. A half-column, horizontally scrolling line was tried first and rejected by the owner after screenshots: it clipped "1 month" mid-word and hid half the options. The listing page shows the chip label ("1 year") instead of "365 nights" whenever the value matches a chip. The min-stay highlight tile still shows a day count, because its copy can't absorb a label; that is an open copy decision.

**Rejected:** (a) **Turning `deliveryType` itself into an array/flags value.** It is a simpler model, but a breaking contract change for any client still reading the scalar. (b) **Two boolean columns** (`OffersPickup`/`OffersCourier`). They don't extend to a third handover mode without another migration, and the enum already existed. (c) **Keeping the address input next to the map button.** The owner explicitly asked for its removal.


**Amended 2026-10-06 (superseded in part by ADR-024).** Section 2's "the pickup location is now only the map pin, via Show on map, which opens the existing picker" no longer describes the system. There is **no per-listing pin**: the wizard's pin picker and district select are gone, step 3 shows a read-only "Pickup area" card derived from the owner's home point, and the picker itself moved to `shared/ui/location-picker/` where it edits the **user's** point, not the listing's. The delivery-options model (flags column mirrored to the legacy field) and the absence of a street-address input are unchanged.

## ADR-018: The refundable deposit is redefined as a loss & damage compensation amount, required and never collected
Date: 2026-09-17 | Area: backend + frontend (listing field, create/edit wizard, item and booking pages)

`Listing.DepositAmount` was an optional "Refundable deposit": money the renter was implied to hand over and get back. DoRent processes no money (ADR-014, Terms), so the label promised a transaction that nobody runs. It had also been unsettable since the Flow A redesign (`c7fd49e`, `2c67d3d`) dropped the input from both the wizard and the edit form, so only seeded listings carried a value. Tigran redefined the field as what owners actually need: **the amount the renter owes the owner if the toy is lost, seriously damaged, or not returned.**

**1. Semantics: nothing upfront, and the amount is a cap.** No money moves at booking or pickup. Lost or not returned means the full amount. Damage is agreed between owner and renter and never exceeds it. The copy states all three facts wherever renters meet the amount, and deliberately contains no claims, guarantee, insurance or refund language — ADR-014's rule, applied to a field that previously broke it.

**2. Full rename, not a relabel.** `DepositAmount` → `CompensationAmount` in the entity, DTOs, wire contract (`compensationAmount`) and UI models, via migration `RenameDepositAmountToCompensationAmount`, a pure `RenameColumn`. Existing values carry over unchanged. The JSON rename breaks stale clients; accepted because the SPA and API deploy together, so no alias was kept.

**3. Required, 1,000–10,000,000 AMD.** `[Required]` + `[Range]` on create; the same range, optional, on the partial update, which stays in the non-content group and never re-triggers moderation (a number cannot carry disallowed text). Old listings without an amount are **not** hidden or re-moderated: they read "Not specified" until the owner edits, and the edit form then requires it.

**4. "Not specified" is shown, never hidden.** On the item page and in the booking breakdown an absent amount renders as "Not specified" rather than removing the row. Two listing generations that look identical but behave differently would teach renters that no row means "nothing to pay, ever". **An amount counts as set only when it is a finite number > 0** (`isCompensationAmountSet`, one shared helper): the old validator allowed 0, the rename preserved it, and treating 0 as "Up to 0 ֏" in some places and "Not specified" in others was caught by `/code-review`.

**5. Owner-loud, renter-quiet.** The owner sets it in its own card on wizard step 3 ("Protects you — not income"), so it never reads as earnings. For the renter it is informational: a specs tile and pickup row at the same weight as age and condition, and in the booking breakdown the only dashed, muted row, excluded from the total, with a line under the total saying so and an info popover with the three facts.

**Deviations from the Claude Design spec, all deliberate:** amounts use `DramCurrencyPipe` (`45,000 ֏`), not the mock's space-grouped `45 000 ֏`; the copy-deck sidebar line promising "free cancellation up to 24h" was not used (no such policy exists — the implemented mock text had no such claim); the mock's service fee, booking-frequency and reply-rate content around the new row stays excluded per ADR-014; the hygiene row moved to `pi-sparkles` so compensation could own the shield.

**Open consequence:** bookings do not snapshot the amount — `BookingResponse`/`BookingDetailResponse` read the listing's current value — so an owner who raises it after a booking exists changes what that renter's booking page shows. Harmless while DoRent collects nothing; revisit if the agreed figure ever needs to be evidential.

**Rejected:** (a) **Keeping it a prepaid refundable deposit** — the platform cannot back the refund promise. (b) **Letting each owner choose deposit vs. compensation** — two models, two sets of copy, one confused renter. (c) **A renter consent checkbox at booking**, optionally stored — Tigran chose information over a click-through; a stored consent would imply DoRent arbitrates. (d) **Relabelling the UI only and keeping `DepositAmount` in code and schema** — cheaper now, a permanently misleading name. (e) **Hiding the row when no amount is set** — see 4.

## ADR-019: DoRent is single-currency AMD, and `DramCurrencyPipe` is the only way a price reaches a screen
Date: 2026-09-22 | Area: frontend (price rendering, i18n) + backend (notification meta, seed, validation)

The app shipped rendering prices through Angular's `currency` pipe with no explicit code, so it fell back to the default locale currency and showed US dollars — while the product operates in Yerevan. Trello #71 raised it. The decision and the migration both landed on **2026-07-20**, but were never written down: `knowledge/mistakes.md` has been citing a nonexistent "ADR-007 moved the app to dram-only pricing" (ADR-007 is Leaflet maps). This record exists so the next person does not rediscover the reasoning from migration SQL.

**1. One currency, Armenian dram, no per-listing choice at the product level.** DoRent does not multi-currency. There is no conversion, no rate, no locale-dependent currency selection. `Listing.Currency` exists as a `nvarchar(3)` column and rides along in the DTOs, but **it is not authoritative for display** — see 5.

**2. Stored values were reinterpreted by a data migration, not by relabelling.** Prices had been authored as dollars (a $6.00/day toy). Labelling the same stored number as dram would have made every listing ֏6/day. Migration `20260720191612_BackfillUsdListingsToAmd` is data-only: it snapshots every USD row into `__BackfillUsdListingsToAmd_Snapshot` (the rollback path), multiplies `PricePerDay` and `DepositAmount` by a **hard-coded 400 AMD/USD** with `ROUND(x, 0)`, sets `Currency='AMD'`, and recomputes `Bookings.TotalPrice` for the affected listings. A frozen rate, not a live one: this converts a historical unit, it is not an FX feature. Dram is rounded to whole units throughout — AMD is not conventionally used with subunits.

**3. The format is owned by one pipe: `Rental-Ui/src/app/shared/utils/dram-currency.pipe.ts`.** Grouped whole number using `en-US` grouping, then U+00A0, then `֏` — `7,500 ֏`. Angular's built-in `currency` pipe cannot produce this: the bundled `en` locale data has no symbol entry for AMD, so `{{ x | currency:'AMD' }}` renders the literal code (`AMD2,500`), and the CLDR locale that does know `֏` (`hy`) groups with non-breaking spaces, which reads wrong next to every other comma-grouped number in the app (ratings, counts, ages). `DEFAULT_CURRENCY_CODE: 'AMD'` in `app.config.ts` is a registration and a safety net, not the formatting mechanism. `DRAM_SYMBOL` is the single export of the glyph — any UI needing the symbol alone (an input prefix or suffix) imports it rather than pasting the character.

**The space is non-breaking on purpose.** A plain space let a compensation amount wrap mid-value (number on one line, `֏` on the next) wherever the container got tight. Every render site gets this for free by going through the pipe; the few places that build the symbol themselves must use the ` ` escape, written as an escape and never as a pasted literal, because a literal NBSP is invisible in review.

**4. The format has a second owner on the server, and they change together.** `NotificationEmitter.BuildMeta` renders the notification context line (`3 days · 7,500 ֏`) into `Notification.Meta` as text at emit time, and the UI prints that string verbatim (`notification-card.component.html`). It is a denormalised snapshot, so it cannot be reformatted retroactively. It is pinned to `InvariantCulture` for exactly the reason the pipe pins `en-US`: the grouping must not depend on where the process runs. **Changing the dram format means changing both places in the same commit.** The rejected alternative was to ship numeric fields (`days`, `totalPrice`) on the notification DTO and format in the UI — correct, and it would also fix the hardcoded English `"day"/"days"` in that string, but it is a contract change for one line of text, and the English-in-notifications problem is app-wide and wants its own pass, not a currency-shaped slice of it.

**Known consequence, accepted:** notification rows written before 2026-09-22 still read `7500 AMD`. No backfill — regex-editing free text in a table of user-visible strings risks more than it fixes, and notifications age out of view on their own.

**5. `Listing.Currency` is deliberately left as an un-allow-listed free string.** Validation only checks it is 3 characters (`CreateListingRequest`), the service upper-cases it and defaults an empty value to `"AMD"` (`ListingsOwnerService`), and it is absent from `UpdateListingRequest`, so it is immutable after creation. Nothing in the UI ever reads it: the pipe renders `֏` unconditionally. **Therefore a direct `POST /listings` with `"USD"` is stored as USD and then displayed as `֏` — a silently mislabelled price.** Tigran's call (2026-09-22), made with that consequence stated: leave it. Writing to the API directly is not a path untrusted clients have, and the cheap fixes both cost more than the risk — an allow-list adds a validation rule nobody can trip through the product, and removing the column touches ~12 DTOs, the UI models and a migration for a field that is already effectively a constant. Revisit if DoRent ever opens a public write API or adds a second market.

**Rejected:** (a) **Display-only change for new listings** — leaves two generations of listings whose identical-looking numbers mean different amounts, with nothing on screen to tell them apart. (b) **A currency code per listing, honoured at render time** — real multi-currency (rates, a base currency, historical rates for past bookings) for a product that serves one city and moves no money. (c) **Registering the `hy` locale and using Angular's `currency` pipe** — see 3; it brings CLDR's NBSP grouping into every price and still needs `registerLocaleData` the app otherwise does without. (d) **Formatting prices in an `Intl.NumberFormat` call at each site** — the same reason there is one pipe: three call sites drifted within a month before it existed.

## ADR-020: The production stand is publicly reachable, and there is no access gate in front of it
Date: 2026-09-25 | Status: accepted (**supersedes ADR-009**) | Decided by: Tigran, after the contradiction was surfaced

**Decision:** `dorent.am` and `www.dorent.am` are open to the internet. There is no Cloudflare Access application, no email one-time-code gate, no IP allowlist and no HTTP auth: the whole surface — SPA, `/api/`, `/uploads/`, `/hubs/` — answers anonymous requests, exactly as it has since the 2026-07-13 deploy. `deploy/smoke.sh` therefore runs in **PUBLIC mode** (no `CF_ACCESS_CLIENT_ID`/`CF_ACCESS_CLIENT_SECRET` in the server `.env`), and that is the correct, intended mode, not a misconfiguration. `DEPLOY-PRODUCTION.md` section k is marked not-implemented and kept as a recipe.

**Why this ADR exists at all:** ADR-009 (2026-07-26) recorded the opposite decision as `accepted`, and nobody implemented it. For two months a recorded decision and production disagreed, while `smoke.sh` — whose newest check was written precisely to prove the gate stays closed — silently skipped that check on every deploy, because its mode switch is the *presence* of the service-token credentials, and absence means "run the old public checks". It was found only because this card's investigation probed the public hostnames for an unrelated reason. Rule 0 exists for this: the fix is to make the record match reality, not to leave two versions of the truth.

**Why keep it open (Tigran, 2026-09-25):** the gate was never a product requirement, it was a precaution, and the cost of that precaution is paid every time the owner opens the site on a phone. Two months of the stand being open produced no incident. Recording the stand as public also makes the real exposures visible and rankable instead of hidden behind a gate that does not exist.

**Consequences accepted knowingly:**
(a) `POST /api/auth/login` is reachable from anywhere. The mitigation that does exist and is deployed: the `auth` rate-limit policy, 5 requests/minute per IP, on `login` and `register` (`RateLimiterExtensions`). There is still **no account lockout** and no MFA.
(b) `showcase@dorent.am` has the password `Demo1234`, published in a public GitHub repository — ADR-005's knowingly-accepted trade-off. With no gate, that account is loggable-in by anyone who reads the repo. ADR-005 already says to revisit it before any real launch; ADR-020 does not change it, but it removes the only thing that was arguably compensating for it.
(c) `/api/categories`, listing data and `/uploads/` are public reads. That is what a marketplace is, so this is not a new exposure — it is the product.
(d) The `access-gate-*` checks in `smoke.sh` will never execute. Keep the dual-mode code anyway: it costs nothing and it is the ready path back.
(e) Anything that later *does* need to be private (an admin surface, a metrics endpoint) needs its own mechanism; there is no perimeter to hide behind.

**Rejected:** (a) **Implement ADR-009 now.** It is dashboard-only, free, and would have taken minutes — declined by Tigran for the usability reason above, with the exposure spelled out first. Recorded as a live option rather than a closed one; the runbook is intact in `DEPLOY-PRODUCTION.md` section k. (b) **Quietly leave ADR-009 as `accepted`** and open a card to enable Access "later" — that is the shape the situation already had for two months, and it is precisely the failure. An unimplemented accepted ADR is worse than a recorded decision not to implement it. (c) **IP allowlist** — already rejected in ADR-009 for a reason that still holds (the phone's IP is dynamic).

**Related:** ADR-009 (superseded), ADR-005 (the showcase password), ADR-003 (the tunnel, and the smoke script this gated), M-047.

## ADR-021: A user changes their own password through `PUT /api/auth/me/password`; it does not revoke sessions, and a wrong current password is a 400
Date: 2026-09-25 | Status: accepted | Area: auth surface (backend + Angular) | Trello #49

**Context:** the auth/identity surface had **no recorded decision of any kind** before this one, and the product had no way for anyone to change their own password — `AuthController` was `register` / `login` / `external` / `me` / `me/preferred-language`. That gap is what made Trello #49 ("change the bootstrap admin password") unexecutable as written: the card assumed a profile screen that has never existed. This ADR records the auth-surface decisions the feature forced.

**Decision:**

**1. One endpoint, `PUT /api/auth/me/password`**, `[Authorize]`, body `{ currentPassword, newPassword }`, **204 No Content** on success. It sits under `/api/auth/me/*` beside `me/preferred-language` because that is where "operations on the authenticated caller" already live; there is no `ProfileController` and this ADR does not create one.

**2. Re-authentication is required in-band:** the caller sends the current password even though the request is already authenticated. A valid token alone is not sufficient to change the credential that token was minted from.

**3. A wrong current password returns 400 (`auth.invalid_current_password`), not 401.** In this codebase 401 is reserved for `*.unauthenticated` — "there is no valid token" — and the Angular client reads a 401 as an expired session (`auth.effects.ts` passes `unauthorizedMessage: 'Your session has expired. Please log in again.'`). Returning 401 for a typo would tell the user they had been logged out. The other two new codes, `auth.password_not_set` (the account signs in with an external provider and has no local password) and `auth.password_unchanged`, are 400 for the same reason: they are input problems, not authentication problems. All three carry the machine-readable `errorCode` extension that `ServiceErrorProblemDetailsExtensions` already emits, and all three are registered in `Rental-Ui/src/app/api/api-error.model.ts`.

**4. Its own rate-limit policy, `password-change` (5/minute per IP), not the existing `auth` policy.** `auth` is one shared per-IP bucket for anonymous `login` and `register`; attaching this endpoint to it would let a password change consume the owner's login attempts from the same IP, and would couple the new integration tests to the alphabetical class-ordering assumption that `Api/RateLimitingTests.cs` depends on. Separate policy, separate counter.

**5. Changing a password does NOT invalidate tokens already issued** — including the caller's own, and including sessions on other devices. `User` has no `SecurityStamp` / `PasswordChangedAt` / token-version column, and `IJwtTokenService` issues a bare access token with no `jti` denylist and no refresh token, so there is nothing to revoke against. A stolen token therefore survives a password change for the remainder of its lifetime (1 hour). Stated as a known limitation, not hidden: real revocation needs a schema change plus a token-validation hook, which is separate work and is not smuggled into a security-hygiene card. **Never describe this feature, in UI copy or in docs, as "signing out other devices".**

**6. Still no password *reset*.** `IEmailService` is a development stub, so a user who has forgotten their password has no self-service path — this endpoint only helps someone who still knows their current one. Carded separately.

**7. No EF migration.** `User.PasswordHash` (`nvarchar(512) NOT NULL`) has existed since `20260414091032_InitialCreate`; the feature writes an existing column.

**Fixed in the same change, because the feature needed the same guard:** external-auth users are created with `PasswordHash = string.Empty` (`AuthService.ExternalAsync`), and `BCrypt.Net.BCrypt.Verify(x, "")` **throws `SaltParseException` rather than returning false**. So a password login against a Google-only account returned **HTTP 500 instead of 401**, and still burned a rate-limit permit. Both `LoginAsync` and `ChangePasswordAsync` now check for an empty hash before verifying; login reports the generic `auth.invalid_credentials`, so it never reveals that the account exists or that it is external-auth. This was invisible to the test suite because `TestSupport/FakePasswordHasher` returns `false` on an empty hash instead of throwing — the M-013 shape, and the reason the new tests exercise the real `BcryptPasswordHasher`.

**Frontend shape (recorded because it is a first in two ways):** the form is a dedicated page, `/profile/security`, the **first child route belonging to the `profile` feature itself** (the existing four all load components from other features). Its state is component-local, following `features/reports/.../report-dialog` — a one-shot request/response with nothing to keep in sync — and deliberately **not** the `updatePreferredLanguage` pattern, which dispatches one action and swallows failures silently; a password change must report its outcome. The "passwords match" check is the **first cross-field `ValidatorFn` in the application**.

**Rejected:** (a) **Rotate the production admin password by writing a bcrypt hash straight into the database** via an operator-run script that prompts for the password, so it never reaches an agent or the chat — this closes the exposure the same day with no deploy, and was the orchestrator's recommendation; declined by Tigran in favour of fixing the product gap properly. The cost of that choice is recorded plainly: the compromised password stayed live on a publicly reachable login for the length of a release that also carried 4 unapplied migrations. (b) **Teach `AdminBootstrapRunner` to overwrite an existing admin's password from `.env`** — needs a deploy anyway, contradicts its documented create-only contract, and puts the new plaintext password back on disk in `.env`. (c) **Returning 401 for a wrong current password** — see 3. (d) **Forcing a local logout after a successful change** — theatre while tokens cannot be revoked (see 5), and it would imply a guarantee the system does not make. (e) **Extracting the 8/128 password length rule into a shared constant** — `LoginRequest` and `RegisterRequest` each carry the literals today; a third copy keeps one convention instead of introducing a second, and the extraction is a standalone refactor.

**Amended 2026-09-27 — passwords are capped at 72 UTF-8 bytes where they are created, and uncapped where they are verified.** `/code-review` found, and confirmed empirically against the pinned BCrypt.Net-Next 4.2.1, that BCrypt ignores everything past **byte 72** of a password: `Verify(80×'a' + "DIFFERENT!", hash_of(80×'a' + "TAIL1234"))` returns `True`. The DTOs allowed 128 *characters*, so three things followed. A password longer than 72 bytes was only partly protective; **a wrong current password sharing the first 72 bytes of the real one was accepted** by the new endpoint; and changing only the tail was reported as `auth.password_unchanged`. Armenian and Russian characters are 2 bytes in UTF-8, so for those the real ceiling is about **36 characters** — well inside the range a person might actually choose, which is what moved this from trivia to a defect.

**The rule, and the asymmetry is the whole point:**
- Where a password is **created** — `RegisterRequest.Password`, `ChangePasswordRequest.NewPassword` — it is rejected above 72 UTF-8 bytes with `auth.password_too_long` (400).
- Where a password is **submitted for verification** — `LoginRequest.Password`, `ChangePasswordRequest.CurrentPassword` — there is **no such cap**, deliberately. Anyone who already holds a password longer than 72 bytes must still be able to type it in full and get in; capping the verification side would lock them out of their own account, turning a silent weakness into a hard outage.

**Measured in bytes, not characters,** via `Encoding.UTF8.GetByteCount`. A character-based cap *is* the bug: 72 Armenian characters are 144 bytes and would sail straight past it.

**Enforced in the service with an error code, not as a DataAnnotation.** A DataAnnotation failure produces a ModelState 400 with **no `errorCode` extension**, which the Angular client cannot map, so the user would be shown the raw English framework string. This follows the convention already set by `UpdatePreferredLanguageRequest`, which carries zero DataAnnotations and whose allow-list lives in `AuthService` returning `auth.invalid_language`.

**Also removed in the same change:** `[MinLength(8)]` on `ChangePasswordRequest.CurrentPassword`. A minimum length on a password being *verified* is meaningless — it either matches the stored hash or it does not — and it was harmful twice over: a short entry failed model binding and surfaced an untranslated `The field CurrentPassword must be a string or array type with a minimum length of '8'`, and it would have permanently locked out any account whose password predates the 8-character rule. Such accounts are creatable today: neither `AdminBootstrapRunner` nor `DemoContentBootstrapRunner` validates password length at all.

**Rejected:** (a) **Cap at 72 on the verification side too, for symmetry** — symmetry is exactly wrong here; see the asymmetry above. (b) **Truncate silently to 72 bytes on the way in** — makes the product agree with BCrypt while still lying to the user about what protects their account. (c) **Leave it and document it** — the residual attack needs an existing session plus knowledge of the first 72 bytes, so the exploit is unlikely; rejected anyway because the user-facing defect is the honest one: a form that accepts a long passphrase and silently uses only its beginning. (d) **Replace BCrypt with Argon2id or PBKDF2**, which have no such limit — the correct fix at the root, and out of scope by a wide margin: it re-hashes every stored credential and is a library decision of its own. Worth revisiting before any real launch, together with ADR-005.

**Known residue, accepted:** accounts created before this cap may still hold passwords longer than 72 bytes. They log in normally, and the `auth.password_unchanged` false positive can still reach them if they try to change only the tail. Nothing migrates them; the next password they set is capped.

## ADR-022: CI provisions a real SQL Server, and "ready" means a login that answered
Date: 2026-09-27 | Status: accepted | Decided by: Tigran | Area: build & delivery topology (`rental-api`)

**Decision:** `.github/workflows/backend-ci.yml` runs a `mcr.microsoft.com/mssql/server:2022-latest` **service container**, and `SqlServerTestDatabase` takes its server from `RENTALPLATFORM_TEST_SQLSERVER_CONNECTION_STRING` when that variable is set, falling back to today's `Server=.;Trusted_Connection=True;TrustServerCertificate=True;` when it is not. A developer's machine therefore needs no setup and behaves exactly as before; CI gets a real database and runs the whole suite.

**Why this was not optional.** Two tests — `ConversationsStoreModerationConcurrencyTests` — exist precisely because SQLite cannot model what they assert: a concurrency convergence under real locking, and the **real** `DeduplicateModerationConversations` migration executing against a real engine. They were written against SQL Server on purpose. The alternative on the table was to skip them when no server is reachable, which would have meant they run on exactly one machine in the world and CI's green light quietly stops covering the migration that rewrites production conversation rows.

**How this went unnoticed for six weeks, which is the part worth remembering.** The tests arrived in `dc9fc69` (2026-09). The last green CI run before this was **2026-08-14**. In between, no pull request to `main` was opened — and the workflow triggers only on `push`/`pull_request` to `main`. So CI simply never ran. It was not red-and-ignored; it was *absent*, which is worse, because absence produces no signal at all. The change-password PR (ADR-021) was the first to execute those tests, and it took the blame for a failure it did not cause. **A CI that only runs on PRs to `main` tells you nothing about a long-lived `dev` branch.** Whether to also trigger on pushes to `dev` is left open deliberately — it is a separate decision with its own cost, and nobody should infer it from this record.

**Readiness is defined behaviourally, not structurally.** The service container's healthcheck is `sqlcmd ... -Q 'SELECT 1'` — an actual login that answered — plus an explicit retry step from the runner before `dotnet test`. "The container is up" is not readiness: the rehearsal caught the exact window where SQL Server accepts TCP but answers `Login failed for user 'sa'`, and a port check would have sailed straight through it. This is M-005's lesson (the `MigrateAsync` vs just-started-SQL-Server race) applied one layer out.

**Two implementation facts that are easy to get wrong, recorded so the next person does not rediscover them:** in that image `sqlcmd` lives only at `/opt/mssql-tools18/bin/sqlcmd` and is not on `PATH` (and needs `-C` for the self-signed certificate); and Docker registers a string `--health-cmd` as `CMD-SHELL`, so `$MSSQL_SA_PASSWORD` expands **inside** the container and the password does not have to be duplicated into the options line. The password reaches `sqlcmd` through `SQLCMDPASSWORD`, never `-P`.

**The SA password is a literal in the workflow file and is deliberately not a GitHub Secret.** It belongs to a container that exists for one job and is reachable only from that job's network. Putting it in Secrets would imply a confidentiality property it does not have, and add a moving part to every fork and every re-run for nothing. This is a different judgement from the production `MSSQL_SA_PASSWORD` (ADR-003), which guards real data and lives only in the server's `.env`.

**One correctness fix rode along, and it is load-bearing:** the per-test database connection string is now built with `SqlConnectionStringBuilder` swapping `InitialCatalog`, instead of the old `$"Server=.;Database={name};..."` interpolation. The interpolation silently discarded every keyword of a supplied connection string, credentials included — so it would have thrown away exactly the SQL authentication CI depends on.

**Rejected:** (a) **Skip the two tests when SQL Server is unreachable** — fastest unblock, and rejected because a suite that goes green without running its only real-engine tests is worth less than it appears; the skip would have been invisible in the badge. (b) **Port them to SQLite** — deletes the reason they exist. (c) **Merge with CI red** — normalises a red pipeline, and this incident is evidence of how fast an unobserved CI rots. (d) **Put the SA password in GitHub Secrets** — see above.

**Related:** ADR-003 (the production SA password, a genuinely different case), ADR-021 (the PR that surfaced this), M-005 (the same race, one layer in).

## ADR-023: A production deploy carrying an EF migration is rehearsed against a restored backup first
Date: 2026-09-27 | Status: accepted | Decided by: Tigran | Area: delivery process (production)

**Decision:** any production deploy that carries an EF migration is rehearsed on the server **before** it touches the live database:

1. Take a fresh backup and prove it restores (`deploy/backup-production.sh`, then `--verify` — they are mutually exclusive modes, so both runs are needed).
2. Restore that same `.bak` into a throwaway database on the box.
3. Run the **newly built** API image against the throwaway database, so the real migration code applies to real data.
4. Compare row counts and column aggregates before and after, and confirm every migration name appears in the log as applied.
5. Drop the throwaway database, then deploy for real.

This applies to **any** migration, not only ones that look risky — the operator's read of "this one is harmless" is precisely the judgement the rehearsal exists to replace. A migration-free deploy needs none of this.

**Why.** The 2026-09-27 release carried four migrations, including a data migration and a column rename over 56 live rows. It was only defensible as a HIGH-risk action because the rehearsal turned "we believe the rename is safe" into a measured before/after — `sum(DepositAmount)` 661 000.00 → `sum(CompensationAmount)` 661 000.00, identical row counts, every migration named in the log.

**What it caught, which is the argument.** `AddConversationModeration` creates a **unique** filtered index. Live data happened to satisfy it, but had two rows collided, the migration would have aborted **mid-release**, after its predecessors had already applied — the worst possible state, because the schema is then neither the old one nor the new one and EF will not re-apply a partially-completed set. Nothing in a code review, a green CI run or a unit test would have surfaced that: it is a property of the production data, and only production data can answer it.

**A migration is not reversible in place.** The rollback for code is `git checkout` + rebuild. The rollback for schema is restoring the backup and losing everything written since. That asymmetry is the whole reason the cheap step goes first.

**Second thing it buys, and it is not incidental:** a rehearsal restores a backup, so it **proves the backup restores**. Cron takes backups without `--verify`, so restorability is otherwise only ever proven when someone remembers — the gap before this work was six weeks. Tying the proof to an event that already demands care means it happens on the deploys that most need a working backup.

**Cost:** roughly ten minutes, on the subset of deploys that carry migrations.

**Operational notes** (learned live, and the reason a naive attempt fails): the `.bak` must be `docker cp`'d and `chown`ed to the mssql uid inside the container; `sqlcmd` takes its password only through `SQLCMDPASSWORD`, never `-P`; `docker compose exec -T` and `run` **consume stdin**, so any piped script needs `</dev/null` on every docker call or its tail is silently eaten. Full sequence in `rental-api/DEPLOY-PRODUCTION.md`.

**Rejected:** (a) **Trust green builds, unit tests and code review** — every infrastructure script in this project that mattered had bugs only a live run exposed (M-005, M-013, and the three found while writing `backup-production.sh`); and none of those layers can see production data, which is what a data migration acts on. (b) **Static review of the generated migration SQL alone** — it would have shown the rename is `sp_rename` and therefore metadata-only, but it could not have told anyone whether a new *unique* index can build against the live rows. Human review of the migration stays required (CLAUDE.md rule 5); this is in addition, not instead. (c) **Keep a permanent staging database** — costs RAM the 2 GB box does not have (ADR-004), and it drifts from production data, which is exactly the thing that needs testing.

**Related:** ADR-003 (backups and the production stand), ADR-004 (why there is no staging environment to rehearse in), ADR-022 (real SQL Server in CI — the same argument one layer earlier), M-005.

## ADR-024: A listing's location IS its owner's home point — one point per user, inherited by every listing
Date: 2026-10-06 | Status: accepted | Decided by: Tigran | Area: data model, API/contract, privacy boundary, display rules

**Decision.** A user has one **home point**: the place renters collect their toys. Every listing that user owns takes its location from it. A listing no longer has a location of its own.

1. **Always inherit.** Moving the home point relocates **every** listing the owner has, in **every** status (Draft, Pending, Approved, Rejected, Archived). `Latitude`/`Longitude`/`PublicLatitude`/`PublicLongitude`/`DistrictId`/`City`/`Country` on `Listings` are a **denormalised copy** of the owner's point, not independent data.
2. **One writer.** `IHomePointService` is the only thing that moves an existing listing's location; `ListingsOwnerService.CreateAsync` is the only thing that sets it initially; `ListingLocationBackfillRunner` repairs drift at startup. Nothing else may write those seven columns.
3. **A relocation is not an edit.** `Status` and `UpdatedAt` are never touched, and a move never re-queues moderation. Asserted at both the service and the migration level.
4. **Yerevan only, for everyone.** A home point is valid iff `IDistrictBoundaryProvider` resolves one of the 12 districts. There is no Armenia bounding box: one lookup, one answer, one error code (`auth.home_point_outside_yerevan`, 400). This applies to renters as well as owners — Tigran's explicit call: a point outside Yerevan cannot be saved at all.
5. **Legacy rows are never retro-validated** (M-038). A migrated home point outside Yerevan keeps working — the account can still edit, archive and restore — but any *new* write from that account is refused. The row is grandfathered; the account is not.
6. **Optional at sign-up, required to publish.** Sign-up step 2 is skippable so renters are not forced to disclose a location. Publishing is gated **server-side**: no home point means 409 `listing.home_point_required`.
7. **City and Country are derived** from the point and fan out with it (Yerevan/Armenia when a district resolves; left as-is for legacy district-less rows). The city input is gone from the create form. Rationale: `City` is an exact-match public filter, so a listing whose city contradicts its pin is invisible to `?city=Yerevan` while pinned visibly in Kentron — two surfaces disagreeing about one row.
8. **Privacy is ADR-008's model, unchanged in mechanism and strengthened in stakes.** Exact pair: the user themselves (`CurrentUserResponse.homePoint`) and admins. Public pair: the geohash-7 centroid, everyone else. District: public. What changed is the blast radius — one leak now exposes a person's entire catalogue, not one listing.
9. **Moving while bookings are in flight is allowed, and renters are notified** (`NotificationKind.Pickup`, Pending/Approved/Active only, fired only when the public pair or district actually changed, best-effort and never able to roll back the move). Blocking the move was rejected: moving house is a real-life event and must not be hostage to platform state; the handover is arranged in chat anyway.

**Migration (`20260927200321_AddUserHomePoint`).** Each owner's point is derived from their **newest listing that has coordinates**; every sibling then collapses onto it. `ListingLocationsBeforeHomePoint` captures every listing's pre-migration location first and is the **only** undo. Geohash and point-in-polygon are never computed in SQL — the derived columns are NULLed and `ListingLocationBackfillRunner` fills them on the next boot, the same mechanism ADR-008's precision upgrade used. Rehearsed in both directions on a copy of real data before merge, per ADR-023. **The tape table must be dropped in a later cleanup migration once the production result is confirmed** — until then it is a permanent copy of every pre-migration exact coordinate.

**Accepted consequences, each decided explicitly rather than discovered.**
- **Collapse is real and visible.** An owner with listings across several districts sees them all move to one point. Measured on real data: `owner@rental.local` 19 distinct pins across 4 districts collapsed to 1 pin in Kentron.
- **The production showcase is split per district** (13 owners) so the public map and district filters stay meaningful. Those accounts get **cryptographically random passwords** and are never usable for login — ADR-005's published-password trade-off stays at the one demo-login account it was accepted for, and is **not** widened to thirteen.
- **The home page's hero map sends the home point with no radius chosen** — the only exception to "coordinates travel only with a radius" (see the ADR-015 amendment). Accepted: the map is "Toys near your home" and cannot be centred without it.
- **`GET /api/districts/at` carries coordinates in the query string**, so they land in access and Cloudflare logs, including during sign-up before the account exists. Raised as a Medium security finding and **accepted as-is by Tigran**; recorded here so it reads as a decision rather than an oversight. Revisit by moving it to a POST body if log retention or access ever widens.
- **`HomePointUpdatedAt` is stamped with the deploy time** for migrated users, so the profile card shows a date the user never chose. Cosmetic, accepted.
- **Known drift from the design boards**, deliberate: distance badges do not appear until a radius is picked; the picker's district chip tints the whole chip rather than only its icon tile for the ok/error states; the radius filter's denied card keeps a `color-mix()` instead of a token.
- **Known debt:** `shared/ui/home-point-map` imports the district model, its display helper and `getDistrictAt` from `features/listings` — a shared-to-feature dependency. Tigran chose to leave it rather than move districts into `shared/` mid-feature.

**Rejected.** (a) **Join through `Owner` instead of copying** — correct in theory, and it would rewrite every ADR-008 query path, both composite indexes and the one exact-coordinate seam; the copy keeps all of that byte-identical, at the cost of an invariant with one writer and a startup repair. (b) **Letting a listing keep its own pin as an override** — `LocationKind.HandoverPoint` stays reserved and unused; an override is the "city contradicts the map" class of bug by construction. (c) **An Armenia bounding box as a cheap pre-check** — two "wrong place" answers mean two error codes, and a cheap approximation can accept what the real check rejects, which is exactly the map-says-fine-but-save-refuses disagreement this avoids. (d) **Reconciling `City` in the startup runner** — it would run forever in every environment against the whole table, keep no record of what it changed, and defeat the undo tape; the one-time fix belongs in the step that created the inconsistency. (e) **Showing distance without a radius** — Tigran's call: the renter's home coordinates must not ride along on every catalogue request.

**Related:** ADR-008 (amended — the privacy mechanism this builds on), ADR-012 (amended — clustering), ADR-015 (amended — the hero-map exception), ADR-017 (amended — the per-listing pin is gone), ADR-005 (deliberately **not** widened), ADR-023 (the rehearsal this migration went through), ADR-025 (the notification's copy), M-038 (why legacy rows are grandfathered), M-030 (why both normalisers had to map `homePoint`).


**Amendment 2026-10-06 (the invariant is held by a transaction on one side only, and the migration's idempotency claim was earned).** Two things the code review and its fixes changed about the decision above.

1. **Create is atomic; move is not, and the remaining window is accepted.** `ListingsOwnerStore.TryAddListingAtOwnerHomePointAsync` wraps the owner re-read and the insert in a serializable transaction (matching `BookingsStore.TryCreateBookingAsync`), and `AddListingAsync` was **removed** so there is no unguarded insert path to drift back to. The `.AsNoTracking()` on that re-read is load-bearing, not an optimisation: the context already tracks the `User` read several queries earlier and a tracking query hands the stale instance straight back — proven by breaking exactly that line and watching the listing commit at the pre-move point. **A narrower window remains on the move side:** `SetHomePointAsync` freezes its read of the listing set before its write commits, so a create that commits between those two moments inserts at the old point and is not relocated. Closing it means writing the `Users` row first inside an explicit transaction, which is a change to `IHomePointStore`'s shape; Tigran chose to card it (Trello, Low) rather than make a second structural change before the release. Until then the repair is `ListingLocationBackfillRunner` pass 2 at startup — which on dorent.am means weeks of latency, so the card matters more than its probability suggests. A `rowversion` on `Users` was rejected: it would fire on every write to a user row (profile edits, block/unblock, password changes) and push EF retry plumbing across the Application boundary.
2. **Migration step 3 is now genuinely idempotent, and the reason is narrower than first believed.** A re-run previously re-NULLed `PublicLatitude`/`PublicLongitude`/`DistrictId`, discarding what the startup runner had computed; step 3 now carries a state guard that skips any row already in the state it would write. This matters because ADR-023 has an operator hand-running this SQL against a restored backup, which is exactly where `__EFMigrationsHistory` is not there to prevent a second `Up`. The earlier analysis also claimed a re-run could elect a different `ROW_NUMBER` winner and change `City`/`Country`; that was **tested in isolation and does not fire** — step 3's first run already gives every listing of an owner the winner's City/Country, so whichever row a second run elects carries the same values. The state guard is the whole fix. The CTE was additionally re-sourced from the undo tape, which changes no observable outcome and is kept only because `l.[Latitude] IS NOT NULL` becomes vacuous after the first run — a filter that no longer filters is a trap for the next reader. **One first-run consequence, stated rather than buried:** the row step 2 took the home point from keeps its existing derived pair instead of having it NULLed and recomputed; the values were derived from the coordinates that row still has, so they are consistent. One row per owner. **Residual, not fixed:** on a second run, listings created *after* the migration join the winner pool, so a legacy owner whose run-1 winner carried a non-Armenian `Country` could see the catalogue flip to "Armenia" after they publish again. Policy for legacy non-Armenian rows is undecided; production holds none today.
3. **`Country` was removed from `UpdateListingRequest`.** It was the last writable location field, and nothing reconciles it, so `{"country":"Neverland"}` stuck forever beside a Yerevan district and pin. The removal also exposed a testing asymmetry worth recording: the create payload had a guard asserting the five derived fields are absent, the update payload had none — which is why `Country` survived three separate removal waves and was caught only by review. The update guard now mirrors the create one.

## ADR-025: Notification copy is rendered server-side, at emit time, in the recipient's language
Date: 2026-10-06 | Status: accepted | Decided by: Tigran | Area: API/contract, i18n

**Decision.** `NotificationKind.Pickup`'s title and body are built by `NotificationCopy` **when the notification is emitted**, in the recipient's `PreferredLanguage` (en/hy/ru) with an English fallback, and stored as text. Tigran's requirement: a notification is in the language the user has chosen, or the default language if they have chosen none. The district name is localized too, and there is a separate variant for a district-less point.

**Why.** `Notification` already documents a "copy produced server-side" contract that the client relies on, and all nine existing kinds are stored text. Rendering per recipient at emit honours both that contract and the requirement, with no schema change and no client work.

**Accepted cost.** A user who switches language later still sees old notifications in the old language, and the other nine kinds stay English until someone converts them. Both are consequences of storing text, and both are acceptable because a notification is a record of a moment.

**Rejected.** (a) **Store a key plus parameters and translate in the UI** — always current-language and the obvious long-term shape, but it breaks the stated server-side-copy contract for one kind out of ten, needs schema plus client changes, and would leave the feed rendering two different ways. Revisit when all ten kinds are converted together. (b) **English only** — contradicts the design and the requirement.

**Related:** ADR-024, ADR-013 (what a notification may disclose — the pickup body carries a district name, never coordinates or an address).

## ADR-026: The agent system — a fixed roster, least privilege enforced by the harness, one report contract, and git delivery split between agent and orchestrator
Date: 2026-10-07 | Status: accepted (Tigran, 2026-10-06)

**Decision.**
1. **Roster.** There are seven custom agents: `backend-dev`, `frontend-dev`, `contract-guardian`, `verifier`, `qa-engineer`, `platform-engineer` and `reviewer`. Read-only exploration and planning use the built-in `Explore` and `Plan` agents. There is no custom explorer, planner or security agent. `general-purpose` is not used for project work, because it carries Edit/Write and can spawn further agents.
2. **Reviewer.** The reviewer runs read-only, in an independent context, over the actual cross-repo diff, checking it against the approved plan and the ADRs. It looks for scope creep and unintended changes, authorization and security defects, ADR conformance and regression risk. It runs on routes that touch the contract, the schema or more than one repo, and on security questions — not on every change. Its report starts with what it actually inspected (M-034, M-050).
3. **Models.** ADR-006 stands, and the reviewer runs on `opus` (see the amendment there).
4. **Least privilege is enforced by the harness, not by prose.**
   - Every custom agent declares a `tools:` allowlist.
   - No custom agent holds `Agent` (nested spawning) or any MCP tool. Only writers hold Edit/Write.
   - `tools:` cannot narrow Bash, so the reviewer's Bash is restricted by a fail-closed PreToolUse hook in the project `.claude/settings.json` (`tools/agent-guards/reviewer-bash.js`), scoped to calls whose `agent_type` is `reviewer`. A hook in the agent's own frontmatter was tried first and was never invoked (M-054).
   - Destructive operations are denied, and risky ones asked for, in the committed `.claude/settings.json`.
   - `main` is protected on the server by GitHub rulesets.
5. **Report contract.** Every custom agent's reply starts with `STATUS: DONE|BLOCKED|NEEDS_INPUT|FAILED|APPROVAL_REQUIRED` and always carries SUMMARY, FILES_MODIFIED, OBSTACLES and NEXT_STEP. Role sections extend it: the verifier's VERDICT, platform's Risk/Evidence and the QA report. A declared status is a signal only — the independent verifier decides whether work is done.
6. **Routing.** Routing is a first-match rule set over facts about the task: does it write, which repos does it touch, does it change the contract or the schema, does it touch production. The rules live in `CLAUDE.md`. Writers run in parallel only when the `PARALLEL_WRITERS` conditions there hold.
7. **Stopping and retrying.**
   - A retry must name what changed since the last attempt.
   - Two failed fixes of the same cause → `BLOCKED`.
   - An environment failure → `BLOCKED` immediately, with no retry.
   - A structural question → `NEEDS_INPUT` (Rule 0).
8. **Commits and pushes are split.** Each agent commits its own work on `dev` — conventional message, the `Co-Authored-By` line, and only the paths it actually changed. No agent pushes, stashes, resets, or touches `main`. The orchestrator reads the diff and pushes, through `ship-dev-pr`.

   **Amended 2026-10-07 by Tigran**, reversing this clause's original "only the orchestrator commits; agents never commit". Two reasons it changed: the agent that wrote the change is the only party that knows which paths are deliberate and what belongs in the message, and the orchestrator was reconstructing both from a diff it had not written — on the home-point release that reconstruction spanned 197 files across two repos. **The review gate does not move.** It sits at the push, which stays the orchestrator's and still requires reading the diff; an unpushed commit is local and reversible, so the irreversible step is still the one a human-owned path guards. `qa-engineer` and `platform-engineer` are included — the carve-out that excluded them is gone, and it was that carve-out which blocked the home-point release-prep doc commit mid-task.
9. **Recovery.** `/rewind` does not cover code edits made by subagents, so the recovery point is git. Before any writer runs, the plan records an execution baseline: each repo's HEAD, a clean tree, and the expected areas of change.
10. **Trace privacy.** Persisted traces hold execution metadata only. They never hold prompts, assistant messages, command text, command output or reasoning.

**Why.** All six agents inherited every tool. That included Edit/Write for a verifier whose whole value is "never fixes code", and `Agent` for all of them. Safety rested on prose. The workflow referred to a reviewer that did not exist, and the review skills scoped themselves to the outer repo, twice (M-034, M-050). Agents used four incompatible report formats. Broad allow rules (`ssh dorent@* *docker compose*`, `git push *`, `dotnet ef *`, `node -e`) left a production volume wipe, a push to `main` and a migration applied to the working dev database (M-051) each one auto-approved command away. Edits made by subagents are invisible to `/rewind`.

**Rejected.**
- (a) **A custom explorer or planner.** It would duplicate the built-ins, which already skip CLAUDE.md and cost less.
- (b) **A dedicated security agent.** The reviewer's scope already covers it.
- (c) **An 11-field report contract.** It is ceremony for small tasks; five fields carry the signal the orchestrator decides on.
- (d) **Narrowing Bash with permission patterns for the verifier and the implementers.** The Claude Code docs call such patterns fragile, and those agents need dotnet, npm and docker. A `git status` diff before and after each read-only agent is used instead, which gives no false certainty.
- (e) **A dedicated checkpoint subsystem.** The plan file, the git baseline and a commit after every step already cover it.
- (f) **`permissionMode` in agent frontmatter.** It is ignored whenever the parent session runs in auto, acceptEdits or bypass mode.

**Known consequences.**
- Production deploy steps that recreate containers (`build`, `up -d`, `git pull` over ssh) now prompt.
- The GitHub rulesets bind Tigran too: there are no direct pushes to `main` for anyone.
- The agents and Tigran share one GitHub identity, so "only the human merges" rests on agents having no path to a merge: `gh` is absent, and credential access and the merge APIs are denied. GitHub itself does not enforce it. A separate machine account for agents would close this gap and is deferred.
- `.codex/` and `AGENTS.md` mirror none of these gates — Codex sessions are outside this model.

## ADR-027: The API learns the client IP from Cloudflare's `CF-Connecting-IP`, relayed by nginx as `X-Forwarded-For` and trusted only from a pinned compose subnet
Date: 2026-10-08 | Status: accepted | Area: production topology, rate limiting, auth surface | Email-verification plan, Phase 0 (D4/R6)

**Context:** every rate-limit policy partitions on `HttpContext.Connection.RemoteIpAddress` (`RateLimiterExtensions.ResolveClientKey`, plus `ResolveUserKey`'s IP fallback). A read-only production investigation (platform-engineer, 2026-10-08, prod at rental-api `3552cdb`) proved that **in production that address is the ui/nginx container for every public request** (`::ffff:172.18.0.3`):
- traffic path: Cloudflare edge → cloudflared (172.18.0.4) → nginx in `ui` (172.18.0.3) → Kestrel in `api`;
- nginx forwards only `X-Real-IP`, which ASP.NET Core never reads; it sets no `X-Forwarded-For`;
- `ForwardedHeaders:Enabled` is `false` in the shipped `appsettings.json`, and no `ForwardedHeaders__*` variable is set, so `UseForwardedHeaders()` does nothing.

So every "per-IP" limit — `auth` (5/min), `password-change`, `booking-create`, `image-upload`, `district-lookup` — was **one global bucket shared by all users**. One abuser could lock everyone out of login and registration. That weakened the only mitigation ADR-020 relies on, and it would have made the email-verification rate limits meaningless. The real client IP does reach nginx: Cloudflare's single-hop `X-Forwarded-For` shows up in the nginx access log. The fix therefore needs no Cloudflare or tunnel change.

**Decision:**
1. **Header source: `CF-Connecting-IP`.** nginx sets `proxy_set_header X-Forwarded-For $http_cf_connecting_ip;` on `/api/` and `/hubs/`. It **overwrites** the header and never appends (`$proxy_add_x_forwarded_for` is forbidden), so whatever `X-Forwarded-For` a client sends never reaches the API. Cloudflare sets `CF-Connecting-IP` itself and overwrites any client-supplied value. The only ingress is the tunnel: ports are bound to 127.0.0.1 and ufw allows only SSH (ADR-003). So a remote client cannot choose its partition. If the header is absent (a request from the host itself through `127.0.0.1:4200`), nginx sends no `X-Forwarded-For` and the API falls back to the nginx address. That fallback is the old behaviour, never a spoofable one.
2. **API trust boundary.** `ForwardedHeaders` is enabled in production with `XForwardedFor` only and `ForwardLimit = 1`. `KnownNetworks` is the stack's compose network, whose subnet is **pinned explicitly** in `docker-compose.production.yml`. Today Docker assigns it (`172.18.0.0/16`), and container IPs change on recreate, so a `KnownProxies` value with a single address would rot. Kestrel listens dual-stack, so the middleware sees IPv4-mapped addresses (`::ffff:a.b.c.d`). A test must prove the trusted network still matches them.
3. **Configuration lives literally in the compose file**, not in `.env`: `ForwardedHeaders__Enabled: "true"` and `ForwardedHeaders__KnownNetworks__0: <pinned subnet>`. The subnet is defined in the same file, so the two cannot drift apart, and no empty `.env` value can reach `GetValue<bool>` (M-016). Separately, `ForwardedHeadersExtensions` stops using `GetValue("Enabled", false)`, which throws on a present-but-empty value, and parses `Enabled` and `ForwardLimit` tolerantly (backlog card "Harden dormant GetValue<bool> trap").
4. **Out of scope:** `X-Forwarded-Proto` is not forwarded. HTTPS termination stays at Cloudflare and scheme handling stays as it is. Rate-limit numbers do not change. They were sized as per-IP limits and become per-IP for the first time.

**Accepted residual risk:** every container on the pinned subnet is trusted to set `X-Forwarded-For`, and so is the docker gateway, which is how the host's own loopback calls arrive. All of those are ours, and reaching them requires SSH to the server. Narrowing trust to nginx alone would need a pinned container IP, which buys nothing against an attacker who already has the host.

**Rejected:**
- (a) **Relaying Cloudflare's `X-Forwarded-For` instead of `CF-Connecting-IP`.** It is proven present, while `CF-Connecting-IP` is documented but not yet observed in our logs. But a client-supplied value survives in it (Cloudflare appends), so it is safe only as long as `ForwardLimit = 1` holds. A single overwritten value has no such dependency. The deploy smoke must confirm the header arrives; if it does not, this ADR gets amended instead of silently keeping the global bucket.
- (b) **nginx `real_ip` module (`set_real_ip_from` + `real_ip_header CF-Connecting-IP`).** It fixes nginx's view, not the API's; the API would still need a header.
- (c) **Reading `X-Real-IP` in a custom partition resolver.** That would be a hand-rolled trust check in place of the framework's tested middleware, and every other consumer of `RemoteIpAddress` would stay wrong.
- (d) **Trusting all networks (`KnownNetworks` cleared to "any").** Any client able to reach Kestrel would choose its own IP.

**Related:** ADR-003 (tunnel only), ADR-020 (public production, the rate limit is the mitigation), ADR-021 §4 (separate rate-limit buckets), M-016, M-044 (real-stack e2e has two buckets, direct and via nginx — unchanged locally, because there is no cloudflared and so no `CF-Connecting-IP`).

**Amended 2026-10-08 (Tigran): an IPv6 client is partitioned by its /64, not by its full address.** `reviewer` found that once the real client IP arrives, Cloudflare's `CF-Connecting-IP` can be IPv6. Every /128 would then get its own bucket. A single subscriber normally holds a whole /64, which is 2^64 addresses, so the 5/min `auth` limit stops limiting anything for an IPv6-capable attacker. Before this ADR, the accidental global bucket at least capped brute force at 5/min in total. By ADR-020 the per-IP limit is the only brute-force mitigation, so this ADR had traded the DoS for a brute-force hole. The fix lives in `RateLimiterExtensions.ResolveClientKey`, the one place every IP partition (and the IP fallback of `ResolveUserKey`) goes through:
- an IPv4 address, or an IPv4-mapped IPv6 address (`::ffff:a.b.c.d`, normalised to IPv4 first), stays as it is;
- any other IPv6 address is masked to its /64 prefix.

**Rejected:** (a) **Cloudflare Pseudo-IPv4.** It is a dashboard setting that is invisible in the repo, and its mapping would need its own verification. (b) **A per-account failed-login limit in addition.** It is stronger against distributed brute force, but it lets anyone lock a known account's owner out. It stays a separate decision and is not part of Phase 0. (c) **Accepting the risk.** It would leave the auth surface weaker than before this ADR.
